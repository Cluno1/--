摘要
近年来，大型语言模型（Large Language Model,LLM）在自然语言理解、文本生成、复杂推理和跨任务迁移等方面取得了显著进展，在零样本和少样本场景下表现出较强的泛化能力。为进一步将语言推理能力延伸到外部环境交互，ReAct（Reasoning+Acting）等Agent范式被提出，用于使模型在检索、工具使用和环境反馈中生成可解释的“推理-行动”序列。然而，面向真实开放场景的LLM智能体仍面临一系列工程化难题，包括检索覆盖不足、工具调用稳定性不足、长上下文遗忘与事实幻觉并存、执行轨迹难以审计、失败恢复机制薄弱以及部署和维护成本较高等问题。这些问题使智能体难以直接应用于对可靠性、可追溯性和权限边界要求较高的企业级任务。
围绕上述问题，本文提出一个可重用、可定制、可评估的LLM智能体方法框架，并实现前后端分离的Agentlz原型系统。该框架以“规划-检索-推理-行动-记忆-反思”的闭环过程为核心，将ReAct范式与检索增强生成（Retrieval-Augmented Generation,RAG）策略结合起来，通过Planner-Executor-Check三段链式工作流对任务分解、工具调用和结果校验进行结构化约束。系统后端基于FastAPI构建统一/v1API，采用路由层、服务层和仓储层分离的分层架构；智能体编排层支持MCP、文件解析、邮件、图像理解等多类工具接入，并记录可回放的调用轨迹；检索层提供文档上传、解析、分片、嵌入、向量索引、多策略召回和融合重排能力；工程支撑层引入WebSocket、SSE、消息队列和多租户鉴权机制，以提升长任务执行过程中的交互连续性、系统吞吐能力和权限治理能力。本文通过构建典型任务场景和评价指标，从任务成功率、执行效率、可解释性、鲁棒性和安全性等维度对原型系统进行验证，并结合典型失败案例分析系统的恢复策略和改进方向。
实验与原型系统验证表明，所提出的闭环架构能够提高复杂任务的可完成性和过程可审查性；检索增强的工具链能够降低生成阶段的事实幻觉风险，并增强答案与证据之间的对应关系；链式工作流、异步执行和实时推送机制能够改善长任务场景下的交互稳定性和系统可维护性。整体而言，Agentlz为面向企业知识问答和多步任务执行的LLM智能体系统提供了一种具有实践可行性的工程参考。

关键词：LLM智能体，ReAct，检索增强，工具调用，工作流编排


Abstract
In recent years, Large Language Models (LLMs) have achieved significant progress in understanding, generation, and reasoning, demonstrating robust generalization capabilities in zero-shot and few-shot tasks. To extend linguistic reasoning into external actions, the academic community has proposed agent paradigms, exemplified by ReAct (Reasoning + Acting), which enable models to form traceable reasoning-action trajectories through retrieval, tool invocation, and environmental interaction. However, in open scenarios, existing LLM agents still face challenges such as insufficient retrieval coverage, unstable tool calling, long-context forgetting and hallucinations, difficulty in auditing trajectories, weak failure recovery, and high engineering deployment costs.
Addressing these challenges, this paper proposes a reusable, scalable, and evaluable LLM agent methodology framework and a decoupled front-end/back-end prototype system, Agentlz. At its core, the system uses a closed loop of Planning-Retrieval-Reasoning-Action-Memory-Reflection, integrating ReAct with Retrieval-Augmented Generation (RAG). The back end leverages FastAPI to construct a unified /v1 API architecture, organizing routes, services, and repositories through a layered structure. On the agent side, a Planner-Executor-Check chained workflow is implemented, supporting multi-source tool routing, including MCP, file parsing, email, and image understanding, as well as trajectory logging. For retrieval, the system integrates vector indexing with multi-strategy recall, providing capabilities for document uploading, segmentation, embedding, and querying. On the engineering side, the system introduces WebSocket pushing, Server-Sent Events, asynchronous execution via message queues, and multi-tenant authentication to enhance interaction experience and maintainability. This study validates the prototype system across task success rate, efficiency, explainability, robustness, and security by constructing representative tasks and evaluation metrics, followed by an analysis of typical failure cases and improvement directions.
Experimental and prototype validation results demonstrate that the proposed closed-loop framework improves the completion of complex tasks and the auditability of execution processes. The retrieval-augmented tool execution path reduces hallucination risks and strengthens answer traceability, while the chained workflow and asynchronous execution mechanisms improve system throughput and interaction stability. Overall, Agentlz provides a practical engineering reference for enterprise-oriented knowledge question answering and multi-step task execution with LLM agents.

Key words: LLM Agent, ReAct, Retrieval-Augmented Generation, Tool Use, Workflow Orchestration

1  引言
1.1研究背景
大语言模型（LLM）的快速发展，使自然语言处理系统从单一文本生成工具逐步转向具备任务理解、知识整合和策略推理能力的通用计算接口。随着参数规模、训练语料和指令微调方法的持续演进，LLM在问答、摘要、代码生成、数学推理等任务中表现出较强的迁移能力，也推动了模型从“被动回答”向“主动执行”的应用形态转变。在这一转变过程中，模型需要能够根据任务目标选择外部知识、调用工具并利用环境反馈修正后续决策，单纯依赖模型内部参数记忆已经难以满足真实场景中的准确性和时效性要求。
ReAct范式是此类转变中的代表性方法之一。该范式通过交替生成推理步骤和行动步骤，使语言模型能够在检索、工具调用和观察反馈之间形成可解释的执行链路，从而在一定程度上缓解链式推理中的事实幻觉问题[1]。然而，ReAct本身并不能自动解决开放环境中的工程不确定性。当智能体面对非结构化文档、异构工具接口、网络延迟、权限控制和长上下文输入时，执行链路很容易受到检索不命中、工具返回异常、上下文信息衰减和输出格式漂移等因素影响。由此可见，LLM智能体的落地瓶颈并不只来自模型能力本身，还来自执行过程缺乏稳定的失败检测、恢复机制和审计边界。
在企业级应用中，上述问题会进一步放大。企业知识问答、自动报告生成、流程辅助决策和多系统协作等任务通常要求答案具备证据来源、操作过程可以回放、工具权限受到控制，并且失败时能够给出明确的定位信息。如果智能体只输出最终自然语言结果，而无法说明调用了哪些工具、依据了哪些文档、在哪个阶段发生偏差，则很难满足合规审计和工程运维需求。因此，面向真实应用的智能体系统需要在方法层面建立闭环执行逻辑，在工程层面提供可观测、可追踪和可治理的系统结构。

1.2研究意义
本文的研究意义在于将LLM智能体的语言推理能力、外部行动能力、检索增强能力和反思校验机制纳入同一个工程闭环之中。与仅在提示词层面对模型进行优化不同，该研究强调通过结构化计划、受控工具路由、证据化检索和结果校验来约束模型的发散性，使智能体在多步任务中不仅能够生成答案，还能够说明执行依据和过程状态。这种设计有助于把LLM从一次性文本生成组件转化为可持续运行、可被审计和可被评测的任务执行单元。
从方法角度看，该研究围绕“规划-检索-推理-行动-记忆-反思”的反馈闭环，对现有ReAct和RAG思路进行工程化整合。规划阶段负责将自然语言目标拆解为可执行步骤，检索阶段为推理过程补充外部证据，行动阶段通过工具调用扩展模型能力，记忆与轨迹记录阶段保存中间状态，反思校验阶段则对结果一致性和目标完成度进行判断。该闭环能够降低单次模型输出对最终结果的决定性影响，减少因局部错误导致整体任务失败的概率。
从工程角度看，Agentlz原型系统将上述方法落实为前后端分离架构和统一API接口，显式暴露任务计划、工具调用、检索证据和校验结果。系统通过多租户鉴权、消息队列、实时推送和结构化日志支持企业场景中的长任务执行和过程治理。这种从方法框架到系统实现的转换，使研究成果不仅停留在算法层面的可行性分析，也能够为企业级智能体平台的开发提供具体的接口设计、数据结构和评测方式。

1.3国内外研究现状与问题
现有研究已经从多个方向探索了LLM智能体的实现路径。ReAct通过推理与行动的交替生成提升了模型在工具使用任务中的可解释性；Plan-then-Act和Chain-of-Thought方法强调先进行任务拆解，再按照计划逐步完成目标；AutoGen通过多Agent对话机制尝试利用协作过程增强复杂任务处理能力[3]；LangChain和LangGraph等工程框架则提供了工具封装、链式调用和图状态编排能力。这些方法和框架为LLM应用开发提供了重要基础，但在生产环境中仍存在较明显的能力边界。
首先，现有框架往往更重视功能扩展和流程自由度，而对执行过程的强约束不足。多Agent对话模式能够在概念上模拟协作，但在高频工具调用和细粒度状态管理场景下，容易出现上下文冗余、职责边界模糊和失败回滚困难等问题。图状态机模式虽然提供了灵活的流程拓扑，但如果缺少统一的规划、执行和校验契约，轨迹记录可能表现为松散节点集合，难以直接服务于审计和离线评测。
其次，RAG系统在工程应用中仍面临召回稳定性和证据一致性问题。单一路径的向量召回容易受到术语差异、表格结构、长文档切分和上下文噪声影响，导致生成阶段获得的证据不足或不准确。即使模型输出了看似合理的答案，如果证据片段无法覆盖关键结论，系统仍然存在事实幻觉风险。因此，检索增强不能被简单视为外部插件，而应当成为智能体执行链路中可评测、可回放和可治理的组成部分。
再次，现有智能体框架对多租户隔离、权限控制、失败恢复和运行观测的关注仍然不足。在企业场景中，工具调用不仅是能力扩展，也可能涉及外部系统访问、敏感文件读取和业务流程触发。如果权限边界被设计为后置插件，而不是内嵌在任务计划和工具路由过程中，智能体就可能在错误工具选择或上下文污染下产生越权风险。基于上述问题，本文将研究目标限定在“受控场景下的单智能体可信执行”，并通过ReAct与RAG融合、Planner-Executor-Check强契约约束和结构化轨迹模型，构建面向企业知识问答与多步任务执行的闭环参考框架。

1.4本文主要工作
本文的主要工作围绕LLM智能体的闭环执行、系统实现和评测验证展开。第一，提出面向受控场景的智能体闭环方法框架，将任务规划、检索增强、工具调用、轨迹记录和结构化校验统一到可追踪的执行流程中。该框架不以无限扩展工具数量或多Agent对话轮次为目标，而是强调在有限工具集合内提高每一步执行的确定性、可解释性和可恢复性。
第二，设计并实现Agentlz原型系统。该系统采用前后端分离架构，后端基于FastAPI实现统一/v1API，并通过路由层、服务层和仓储层划分降低业务耦合；前端基于React-Admin构建管理控制台，通过WebSocket和SSE展示任务进度、链路事件和评测结果。系统在智能体侧支持Planner-Executor-Check三段链式工作流，在检索侧支持文档解析、递归切分、向量嵌入、BM25召回、RRF融合和上下文组装，在工程侧支持异步任务调度、多租户鉴权和结构化日志。
第三，构建多维评测方法，对原型系统在典型任务中的表现进行验证。评测维度包括任务成功率、平均步数、平均耗时、工具失败率、校验通过率、引用命中率、证据覆盖率和权限触发情况。通过对比无检索、RAG、Plan-then-Act和闭环策略等设置，本文分析各模块对任务完成质量和系统稳定性的影响。同时，结合检索为空、工具不可用、格式不合规和权限触发等失败案例，讨论系统的定位能力和恢复策略。

2  相关技术与理论基础
2.1大语言模型与提示工程
大语言模型以Transformer结构为基础，通过大规模语料预训练获得语言建模、上下文理解和模式迁移能力。经过监督微调、指令对齐和人类反馈强化学习后，模型能够在多种自然语言任务中根据指令生成较为符合预期的输出。对于智能体系统而言，LLM并不只是问答引擎，而是承担意图理解、任务拆解、参数生成、工具选择和结果解释等多种角色。因此，模型输出的稳定性和结构化程度会直接影响系统后续执行链路。
提示工程是连接自然语言目标与模型行为约束的重要方法。OpenAI等机构提出的提示工程实践强调明确任务目标、提供示例、限定输出格式和拆解复杂任务[4]。在智能体系统中，提示词不仅用于提高回答质量，还用于约束计划格式、工具参数、校验标准和失败处理策略。如果提示词仅以长文本说明形式存在，模型在复杂任务中仍可能出现格式漂移、任务遗漏或过度生成。因此，Agentlz将提示工程与结构化Schema结合起来，使模型输出尽可能映射到可解析的数据对象，而不是只依赖自然语言结果。
LLM的上下文窗口和向量库常被分别理解为短期记忆与长期知识存储，但二者在实际使用中都会受到信息衰减影响。长上下文会带来注意力稀释，向量检索会因切分边界和语义泛化造成召回偏差。单纯增加上下文长度或提示词长度并不能稳定解决问题。基于这一认识，Agentlz在设计上将提示词版本控制、结构化输出、检索证据和全链路轨迹记录共同作为系统底层约束，用工程机制为模型的不确定输出提供可复盘的依据。

2.2工具回调型智能体范式
工具回调型智能体的核心思想是让LLM根据任务需要调用外部工具，并根据工具返回结果继续推理。与传统单轮问答相比，该范式使模型能够访问实时信息、执行计算、读取文件、调用外部API或与业务系统交互。ReAct模式通过“思考-行动-观察”的交替循环，将模型推理与外部反馈连接起来，使中间过程具备一定可解释性和可调试性。
然而，工具调用并不等同于能力的简单叠加。外部工具通常具有参数约束、权限要求、超时限制和失败模式，模型生成的自然语言计划也可能无法直接转化为合法调用。若缺少工具描述、参数校验和调用边界，智能体容易出现工具选择错误、参数不完整、重复调用和异常结果误用等问题。Agentlz将工具调用建模为具有名称、输入、输出、状态、耗时和错误原因的结构化单元，使工具行为能够被记录、展示和离线分析。
从工程实现角度看，工具回调型智能体需要在模型自由生成和系统确定执行之间建立边界。Agentlz通过MCP工具接入、适配器封装和执行轨迹记录，将工具能力描述为受控接口，而不是任由模型直接生成任意调用。重试、降级、超时控制和权限拦截机制则作为执行层的防御策略，用于应对模型输出不稳定和外部工具不可用带来的风险。

2.3检索增强生成
检索增强生成（RAG）通过“索引-召回-重排-生成”流水线，将外部知识库中的文档片段引入模型上下文，从而减少模型仅依赖参数记忆生成答案的风险。对于企业知识问答、规章制度查询和技术文档分析等场景，RAG能够提供更强的知识时效性和答案可追溯性，是LLM应用工程化落地中的重要技术路线。
RAG系统的关键不只在于是否接入向量库，还在于文档解析、切分策略、嵌入模型、召回方式、候选重排和上下文组装的整体质量。若文档切分忽视语义边界，相关信息可能被分散到不同片段中；若只采用向量相似度召回，术语精确匹配和表格字段可能被忽略；若上下文组装缺少长度控制，模型仍可能受到噪声干扰。因此，Agentlz在文档进入索引前进行格式化解析和带重叠窗口的切分，并保留页码、来源和片段标记，用于支撑后续引用溯源。
在召回策略上，Agentlz采用向量召回与BM25词项召回相结合的混合路径。向量召回用于捕捉语义相近的问题表达，BM25用于提升专有名词、字段名和数值类问题的匹配能力，两路结果再通过RRF进行融合。该设计可以在企业文档长尾问题中降低单一路径召回失败的概率，也为后续评测中的引用命中率和证据覆盖率统计提供可量化基础。

2.4工作流编排与多步执行
多步任务通常需要经历目标理解、步骤拆解、工具调用、结果整合和质量校验等多个阶段。AutoGen等多Agent框架通过可编程对话代理协作驱动LLM完成复杂任务[3]，这一思路体现了通过交互过程降低单一模型输出随机性的尝试。Plan-then-Act和CoT方法则通过显式计划或中间推理过程提升任务分解能力。这些方法说明，复杂任务的关键并不只在于模型是否足够强，还在于执行过程是否有稳定的组织形式。
在Agentlz中，工作流编排采用Planner、Executor和Checker串联的三段契约。Planner负责将用户目标转化为结构化执行计划，Executor根据计划顺序调用工具并记录观察结果，Checker对阶段性输出和最终结果进行一致性评估。该工作流的优势在于，每个阶段都有明确输入、输出和失败判定条件，便于在执行异常时定位问题来源。
与松散任务列表相比，三段链式工作流更适合需要审计和回放的企业场景。规划器输出的步骤可以用于评审任务是否被正确拆解，执行器记录的工具调用可以用于分析失败率和耗时，校验器生成的评分和理由可以用于判断是否需要回退或重新规划。该设计牺牲了一部分流程自由度，但换取了更明确的责任边界和更可控的恢复路径。

2.5关键工程技术栈
LLM智能体系统的工程实现通常涉及后端服务、前端交互、数据持久化、向量检索、异步任务和外部工具接入等多个层面。传统链式框架能够提高原型开发效率，但过度封装也可能遮蔽执行过程中的关键细节，导致离线评测、问题定位和权限审计困难。Agentlz在技术选型上强调接口清晰、状态可观测和模块可替换。
后端方面，FastAPI支持原生异步、自动生成API文档和类型声明，适合构建高并发API服务[6]。系统通过FastAPI提供REST风格接口、鉴权中间件和SSE流式输出；SQLAlchemy负责数据库访问和事务管理；WebSocket负责长任务进度推送；消息队列负责测评、索引构建和工具调用等耗时任务的异步调度。对象存储用于管理上传文件，Redis用于缓存和状态同步，关系数据库用于保存租户、用户、文档、任务和轨迹数据。
智能体与编排方面，系统可接入LangChain、LangGraph或自定义适配层实现模型调用、工具封装和链式执行。检索方面，系统支持pgvector或FAISS向量索引，并结合BM25、RRF和可选重排模型。前端方面，React和React-Admin用于构建管理控制台，Arco Design提供通用交互组件，Axios封装HTTP请求。该技术栈的组合目标不是追求单一框架的完整性，而是为智能体执行链路提供可替换、可扩展和可观测的工程基础。

2.6现有工程框架的能力边界
LangChain等框架为LLM应用开发提供了工具封装、链式调用和记忆组件，在原型阶段具有较高效率。但在复杂企业任务中，执行过程如果缺少统一Schema和轨迹规范，工具调用、检索证据和模型输出会分散在不同日志中，难以形成可审计的因果链路。LangGraph通过图状态机增强流程表达能力，但节点语义高度自由也可能导致计划、执行和校验之间缺少强约束，进而影响结果收敛和离线复现。
AutoGen的GroupChat机制强调多Agent协作和群体讨论，适合探索开放式问题和复杂协作任务。然而，对于单智能体内部的细粒度工具调用，该模式可能引入额外对话轮次和状态冗余。工具失败后的修复逻辑如果依赖开发者在各个插件中分别实现，就难以形成统一的韧性机制。RAG插件同样存在类似问题，许多实现侧重快速接入向量库，而对异构表格、术语匹配、引用标记和证据覆盖的处理不足。
因此，本文没有追求通用图灵完备式智能体框架，而是聚焦“单Agent、有限工具、可审计、可恢复”的受控子领域。该选择使系统能够围绕企业知识问答和多步工具执行建立更清晰的结构化约束。通过多策略召回、三段链式工作流、多租户隔离和结构化轨迹模型，Agentlz尝试在灵活性和可治理性之间取得平衡，为生产环境中的智能体应用提供更稳定的参考路径。

3  方法框架与总体设计
3.1闭环框架概述
Agentlz闭环架构的逻辑起点是提高受控环境下单智能体执行的可靠性，而不是模拟无限复杂的多智能体协作。该框架将智能体任务组织为“规划-检索-推理-行动-记忆-反思”的循环过程，并在工程实现中将核心执行链路固化为Planner到Executor再到Check的线性流程。该流程明确规定每一阶段的输入输出和责任边界，减少任务跳跃、乱序执行和中间状态丢失带来的不确定性。
与开放图编排相比，闭环架构主动限制了流程自由度。任务必须先经过计划生成，再进入工具执行，最后由校验环节判断目标完成度和证据一致性。当校验失败时，系统可以根据失败类型回退到规划或执行阶段，而不是直接输出不可靠结果。该设计在通用性上有所收缩，但对于存在合规审计、权限隔离和结果可追溯要求的企业应用而言，过程可复现性比形式上的高度灵活更为重要。
闭环架构还强调记忆与反思的工程化表达。系统不是简单保存对话历史，而是将计划、工具调用、检索证据、异常信息和校验结果以结构化形式写入轨迹数据。这样既可以支持前端可视化展示，也可以为离线评测、问题回放和工具可信度更新提供基础数据。通过将“思考”和“行动”过程显式化，系统能够在模型不确定输出之外建立一套可检查的执行证据链。

3.2模块划分与接口
Agentlz采用面向接口的模块划分方式，以降低模型调用、工具执行、检索服务和业务数据之间的耦合。Fielding提出的REST架构强调统一接口和无状态约束，以此换取分布式系统的可扩展性和可演化能力[7]。在智能体系统中，执行过程具有较强的上下文依赖，简单套用无状态接口会导致状态碎片化。因此，Agentlz在遵循REST风格的基础上，将状态和上下文封装为结构化对象，并通过任务ID、租户ID和轨迹ID贯穿整个执行链路。
系统模块主要包括入口路由模块、智能体编排模块、检索增强模块、工具适配模块、任务调度模块、权限治理模块和轨迹存储模块。入口路由负责统一接收/v1API请求；编排模块负责Planner-Executor-Check链路调度；检索模块负责文档处理和证据召回；工具适配模块负责MCP、文件解析、邮件、图像理解等工具调用；任务调度模块负责异步任务分发和进度推送；权限治理模块负责租户边界、用户身份和资源访问控制；轨迹存储模块负责记录可回放的中间结果。
在接口设计上，系统避免使用过于粗粒度的工具调用入口，而是为多源工具路由设置明确的参数Schema、权限边界、超时规则和错误返回结构。统一的state/context对象保存运行元信息、检索证据和阶段性输出，避免上下文在不同模块之间以无结构文本传递。面对检索为空、格式偏移和工具异常等情况，系统通过重试、降级和回退机制将失败显式化，为后续修复和评测提供依据。

3.3三段链式工作流
Agentlz的核心工作流由Planner、Executor和Check三个阶段组成。Planner根据用户输入识别任务目标、约束条件和可用工具，生成结构化计划；Executor按照计划顺序逐一调用工具或服务，并将观察结果写入轨迹；Check对阶段性输出、证据来源和最终答案进行一致性检查，根据评分和理由决定通过、修复或中止。
Planner阶段的重点是降低任务理解和工具选择的自由漂移。系统通过强类型提示词要求模型输出WorkflowPlan，其中包含execution_chain、mcp_config和instructions等字段。execution_chain规定工具调用顺序，mcp_config描述可用工具服务，instructions记录执行约束和引用要求。该结构使自然语言目标可以转化为可审查的计划对象。
Executor阶段的重点是将工具行为原子化。每次工具调用被抽象为ToolCall单元，记录工具名称、输入参数、执行状态、输出结果、耗时、错误原因和关联步骤。Check阶段的重点是把目标信息与执行事实进行对齐，通过judge、score、reason和tool_assessments等字段输出结构化评审结果。通过这种三段式设计，复杂任务可以被拆解为多个可控单元，也便于进行策略对比、消融实验和失败定位。

3.4多租户与权限边界
多租户隔离和权限控制在企业智能体系统中不能被视为附加功能，而应作为执行链路的基础约束。LLM智能体在调用工具时可能访问文档、数据库、对象存储、邮件系统或外部API，一旦上下文中混入其他租户信息或工具权限判断滞后，就可能造成越权访问和数据泄露。因此，Agentlz在请求进入系统时即绑定租户标识、用户身份和资源范围，并在工具路由和检索过滤中持续传递这些约束。
系统的权限治理采用“边界前置”和“调用拦截”相结合的方式。边界前置是指Planner生成计划时就需要感知可用工具范围和资源权限，避免计划阶段选择不可访问工具；调用拦截是指Executor在真正调用工具前再次校验租户、角色、文件归属和敏感操作类型。对于高风险操作，例如访问受限文件、调用外部系统或触发批量任务，系统要求记录操作轨迹并保留失败原因。
这种设计会增加中间件校验和状态传递成本，但能够将越权风险控制在可观测范围内。权限错误不会被简单视为工具失败，而是作为可恢复错误返回给Planner，使系统重新选择低权限可用路径或终止任务并提示原因。通过将权限约束嵌入计划、执行和校验全过程，Agentlz能够更好地适配企业级应用对数据隔离和审计留痕的要求。

3.5轨迹记录与结构化数据模型
为了使智能体推理和工具行为具备可追溯性，Agentlz不采用松散日志堆叠方式，而是将关键中间结果组织为结构化数据模型。轨迹记录的目标不是单纯保存运行文本，而是把自然语言计划、工具调用事件、检索证据、异常信息和校验结果转化为可查询、可回放和可统计的数据对象。该设计为前端展示、离线评测、问题定位和合规审计提供了统一基础。
在Planner阶段，系统将模型生成的自然语言计划解析为WorkflowPlan对象，从源头上降低语义漂移风险。Executor阶段将每次工具调用记录为ToolCall对象，保留输入输出快照和状态变化。Check阶段将评审结论记录为CheckOutput对象，并通过工具级评估字段反映单个工具调用对最终结果的贡献或风险。三类对象共同构成可复盘的执行轨迹。
结构化轨迹还可以服务于后续策略优化。例如，某类工具的失败率持续升高时，可以通过ToolCall记录分析失败集中在初始化、参数校验还是返回解析阶段；某类检索任务的证据覆盖率不足时，可以根据召回片段和CheckOutput反馈调整切分或召回策略。由此，轨迹数据不仅是审计材料，也是系统迭代的观测基础。

3.5.1计划结构
计划结构的核心是将抽象目标转化为有序调用链和可执行约束。WorkflowPlan中的execution_chain记录推荐调用顺序，用于约束Executor按计划执行；mcp_config记录MCP服务连接配置和工具能力，用于构建多服务器工具客户端；instructions记录额外执行约束，例如必须先检索后生成、回答必须引用来源、敏感操作需要二次校验等。
该计划结构可以避免模型在执行阶段临时改变任务路线。对于不完整或模糊的用户目标，Planner需要将任务拆解为可逐步验证的子步骤，而不是直接生成最终答案。对于包含外部工具的任务，计划结构还需要说明工具选择理由和输入参数来源。通过这种方式，系统把语言模型的开放生成结果压缩到可校验的结构化空间内，减少后续执行中的不确定性。

3.5.2执行轨迹
Executor层将工具行为抽象为统一的ToolCall逻辑单元。每个ToolCall包含工具标识、所属步骤、输入参数、输出结果、执行状态、开始时间、结束时间、耗时、错误信息和重试次数等字段。该结构一方面支持前端实时展示工具调用过程，另一方面支持离线统计失败率、平均耗时和成本分布。
执行轨迹的价值在于拆解黑盒过程。对于多步任务，最终答案错误可能来自计划拆解错误、检索证据不足、工具参数错误或结果整合失真。若只有最终自然语言输出，问题很难定位；若保留完整ToolCall序列，则可以还原每一步输入输出，判断错误从哪个阶段开始扩散。该机制使系统具备面向生产环境的可审查性和可维护性。

3.5.3校验结果
Check阶段将目标信息（Object）和执行事实（Fact）进行拼接，并交由校验Agent生成CheckOutput。CheckOutput包含judge（是否通过）、score（1—100）、reason（理由）以及工具级评估列表tool_assessments。工具级评估使用micro_score和micro_judge描述单个工具调用质量，可用于问题回放、工具可信度更新和路由策略调整。
校验结果不是简单的终止条件，而是闭环恢复的依据。当score低于阈值或judge为不通过时，系统根据reason和tool_assessments判断应重新检索、修正工具参数、替换工具、缩小任务范围还是中止并提示用户。通过结构化校验，系统能够把“结果不可靠”转化为可执行的修复建议。

3.6失败恢复与反思机制设计
开放执行环境中的失败通常由信息不足、工具不可用、参数不合法、权限受限、网络波动和模型格式漂移等多种因素共同造成。Agentlz将失败恢复（FailureRecovery）视为闭环架构的内生能力，而不是执行失败后的临时补丁。系统通过“在线检测-故障定位-分层恢复”的机制，使任务在受到扰动时仍能尽可能保持可解释和可控。
失败恢复的第一步是在线检测。系统在Planner、Executor和Check三个阶段分别设置检测点，以便尽早发现异常。第二步是故障定位。系统通过steps和tool_calls记录阶段状态、工具输入输出和错误原因，使失败可以定位到具体阶段、具体工具和具体参数。第三步是分层恢复。系统根据失败类型选择重试、查询改写、工具替换、计划重构、任务边界收缩或中止提示。
反思机制主要由Check阶段承担。校验Agent不只判断最终答案是否通过，还需要说明失败原因和修复方向。该机制使系统能够将执行反馈重新输入规划阶段，形成有限次闭环迭代。为避免无限循环，系统设置最大步数和最大回退次数，当达到上限时转为可解释中止，并提示用户补充信息或调整任务范围。

3.6.1失败检测
Planner阶段检测模型是否生成合法结构化计划，重点关注必填字段缺失、工具链为空、JSON解析失败和计划与用户目标不一致等情况。Executor阶段检测MCP客户端是否初始化成功、工具列表是否获取成功、工具参数是否满足Schema、调用是否超时以及返回结果是否符合预期。Check阶段检测judge和score是否达到阈值，默认score不低于80才视为通过。
通过在三个阶段分别设置检测点，系统能够避免错误在链路末端才被发现。例如，计划结构缺失时无需进入执行阶段；工具参数错误时无需等待最终答案生成；校验不通过时无需把结果直接返回给用户。分阶段检测能够降低无效计算成本，也使失败原因更加清晰。

3.6.2失败定位
系统将每一步状态写入steps，将工具调用序列写入tool_calls，将检索证据写入retrieval_context，将校验结论写入check_outputs。当任务失败时，定位过程不再依赖最终自然语言描述，而是可以回溯到“阶段+工具名+输入参数+输出结果+错误原因”的组合信息。
这种定位方式特别适用于长任务和异步任务。对于测评运行、索引构建或多工具任务，失败可能发生在某个批次、某个文档或某个工具调用中。结构化定位能够帮助运维人员快速判断失败属于数据质量问题、工具服务问题、模型输出问题还是权限配置问题，从而减少排查成本。

3.6.3恢复策略
Agentlz的恢复策略以计划重构为主轴，辅以重试、降级和任务边界收缩。若Executor发现工具临时不可用，系统可以进行有限次重试；若检索结果为空，系统可以触发查询改写和多路召回；若工具参数不合法，系统可以回退到Planner重新生成参数；若Check判断结果偏离目标，系统可以要求重新规划或补充证据。
当任务达到预设最大步数或连续失败次数时，系统不再盲目重试，而是转为可解释中止。中止结果需要包含已完成步骤、失败阶段、主要原因和建议补充的信息。该设计避免了闭环系统因无限迭代消耗资源，也为用户提供继续修正任务的明确依据。

3.7工具可信度与路由策略
工具使用的不确定性是LLM智能体工程化落地中的重要风险。不同工具在可用性、响应速度、权限要求和返回质量上存在差异，固定工具顺序难以适应长期运行环境。Agentlz在结构化校验结果中保留tool_assessments字段，将每次工具调用的micro_score和micro_judge记录到工具路由元数据中，用于后续可信度更新。
工具可信度并不是单一成功或失败标记，而是由多次执行轨迹累积得到的统计信号。例如，某工具在特定租户下频繁超时，可以降低其优先级；某工具在数值查询任务中输出稳定，可以在类似任务中优先选择；某工具因权限限制多次被拒绝，则Planner应减少对其依赖。通过将校验反馈转化为路由依据，系统能够在长期运行中逐步形成面向任务类型和上下文条件的工具选择偏好。
该策略仍属于初步设计，后续可以进一步引入强化学习或偏好优化方法。但在当前原型中，基于结构化轨迹的可信度记录已经能够为工具降级、路由排序和故障分析提供基础数据。

3.8设计目标与原则
本文框架与系统实现遵循以下设计原则：
可解释性：最终输出应尽量具备可回溯的计划、证据和工具轨迹。
可审计性：工具调用输入输出、权限判断和异常信息应能够被记录与回放。
可扩展性：工具适配器、检索策略和模型接口应支持替换和扩展。
可评测性：结构化日志应支持统一指标计算、回归测试和消融对比。
安全边界：系统应通过多租户隔离、权限控制和敏感信息治理降低越权与误用风险。
交互连续性：长任务应通过异步执行、进度推送和阶段事件展示降低等待不确定性。

4  系统实现
4.1总体架构
Agentlz原型系统采用前后端分离和后端分层设计。后端基于FastAPI实现统一API入口，并按“路由层-服务层-仓储层”组织业务逻辑；前端基于React-Admin构建管理控制台，用于展示智能体配置、文档管理、评测任务、链路轨迹和运行状态。系统通过消息队列将耗时任务从主请求链路中解耦，通过WebSocket和SSE向前端推送实时进度和链式事件，从而在长任务场景中兼顾交互感知和后端响应弹性。
总体架构可以分为五个部分。第一是API网关与路由层，负责鉴权、参数校验、异常封装和请求分发。第二是智能体编排层，负责Planner-Executor-Check链式执行和工具路由。第三是RAG服务层，负责文档上传、解析、切分、嵌入、索引和召回。第四是任务调度层，负责测评运行、索引构建和异步工具调用。第五是数据与观测层，负责关系数据库、向量索引、对象存储、缓存、日志和轨迹记录。通过这种划分，系统既能支持原型验证，也便于后续在企业环境中扩展。

4.2后端实现
后端实现要点如下：
路由层：按领域拆分路由模块，包括auth、agent、chain、document、evaluation、mcp、uploads、ws等，并在应用入口统一挂载。
服务层：封装核心业务逻辑与跨模块协作，包括智能体编排、RAG文档处理、测评调度、缓存交互和队列投递。
仓储层：封装数据库表的增删改查，将多租户隔离条件、分页排序和过滤谓词抽象为统一访问接口。
异常与响应：采用统一返回结构，区分参数校验错误、权限错误、外部服务错误和内部服务错误，确保接口契约稳定。
外部服务：封装数据库、对象存储、向量库、消息队列和缓存连接，提供可开启或关闭的生命周期治理。
数据库设计：数据库表围绕用户、租户、文档、任务、工具、轨迹和评测结果组织，关键实体关系如图4.1所示。

4.2.1统一响应体与异常处理
统一响应体是前后端稳定联调的基础。Agentlz采用Result语义封装成功和失败状态，将code、message、data、request_id等字段固化为统一结构。无论接口返回业务结果、参数校验错误、权限拒绝还是外部工具异常，前端都可以按照同一格式解析，避免因返回体发散导致交互逻辑复杂化。
异常处理采用入口级注册方式，对HTTP异常、Pydantic校验异常、数据库异常、外部服务超时和未知异常分别进行捕获与转换。异常信息既要满足前端可读性，也要避免泄露敏感内部细节。对于可恢复错误，系统在响应中保留错误类型和阶段标识，便于Planner或Executor进行重试、降级或回退。该机制在接口变更和系统演进过程中降低了定位成本，也为审计日志提供了稳定格式。

4.2.2流式链路接口设计
为降低长推理链路带来的感知滞后，Agentlz使用SSE（Server-Sent Events）搭建流式遥测通道。接口层以/v1/chat为根路径，将Planner、Executor和Check产生的中间结果通过“事件类型-事件内容”的模型增量传输到前端。事件类型包括chain.step、planner.plan、call.start、call.end、retrieval.context、check.summary和final.answer等。
该事件模型将内部执行节点与最终输出解耦。前端可以根据事件类型分别渲染计划列表、工具调用状态、检索证据、评分理由和最终答案，用户无需等待完整任务结束才能了解系统进度。对于失败任务，前端也能展示失败阶段和原因，而不是只显示通用错误提示。流式链路的设计使原本抽象的推理过程转化为透明的阶段事件，提高了交互连续性和过程可理解性。

4.2.3责任链执行与步数上限控制
系统工作流以责任链方式组织，从Root节点依次流经Planner、Executor和Check模块。每个模块接收上游状态对象并产出新的阶段结果，下游模块只能读取经过结构化封装的状态，不能直接依赖上游自然语言文本。该设计减少了模块之间的隐式耦合，也便于在某一阶段失败时进行局部回退。
为防止闭环推理无限循环，系统设置hard_limit和soft_limit两类步数限制。soft_limit用于提示任务可能过长或需要缩小范围，hard_limit用于强制截断执行并返回可解释中止结果。步数上限与重试次数共同构成对不确定性的保守管理，能够防止资源消耗失控，并使复杂长任务保持稳定的执行边界。

4.2.4会话管理与主题发布
系统提供轻量级WebSocket状态管理机制，用于维护“连接-用户-租户”的三元组映射关系。长任务运行过程中，后台消费者可根据任务ID、用户ID和租户ID将进度事件推送到对应连接。WebSocket层以Topic为中心组织发布/订阅模型，用于测评、索引构建、文件解析和智能体运行等场景。
实际设计中提供send_to_user和publish两类传播方式。send_to_user用于向单个用户推送私有任务进度，适合文档上传、个人评测和单次智能体运行；publish用于向订阅同一Topic的多个连接广播状态，适合共享看板和团队任务监控。该模型在交互深度和系统开销之间取得平衡，避免了轮询带来的无效网络流量和重复计算。

4.3智能体编排与工具系统
Agentlz的智能体编排层将提示模板、数据契约和执行引擎进行解耦。提示模板负责描述任务目标、工具使用规则和输出格式；PydanticSchema负责定义强类型I/O协议；执行引擎负责根据结构化计划调用工具、记录轨迹并触发校验。该设计使系统可以在不改变业务流程的情况下替换模型、调整提示词或新增工具适配器。
工具系统采用能力描述和适配器模式。每个工具需要声明名称、描述、输入Schema、输出Schema、权限要求、超时限制和错误类型。Executor根据WorkflowPlan选择工具，并通过适配器处理stdio、http、sse等不同传输方式。工具调用过程产生call.start和call.end等遥测事件，用于前端展示和离线统计。

4.3.1结构化计划生成
Planner模块以自然语言目标为输入，通过强类型提示词生成WorkflowPlan。该计划不仅包含步骤列表，还需要给出工具调用顺序、MCP连接配置、参数来源和执行约束。为降低模型输出不确定性，系统对Planner输出进行结构化解析和字段校验；若解析失败，则启动兜底计划结构，并将失败原因写入轨迹。
结构化计划生成的关键在于把任务理解前置到可审查对象中。对于检索问答任务，计划通常包括问题改写、证据召回、上下文组装和答案生成；对于多工具任务，计划需要包含工具选择、参数构造和结果校验；对于高风险任务，计划还要显式标明权限边界和确认条件。通过这种方式，系统能够在执行前发现明显不合理的任务拆解。

4.3.2多工具接入与日志采集
Executor负责根据计划调度MCP工具栈，并适配不同类型的外部工具。对于HTTP工具，系统封装请求方法、路径、Header、Body和超时设置；对于stdio工具，系统管理进程生命周期和标准输入输出；对于sse工具，系统处理流式事件订阅与增量结果解析。不同工具的底层通信方式被统一映射到ToolCall结构中。
日志采集通过回调机制实现。工具调用开始时产生call.start事件，记录工具名称、输入参数摘要和所属步骤；调用结束时产生call.end事件，记录输出摘要、耗时、状态码和异常信息。为了兼顾审计和隐私，系统可以对敏感字段进行脱敏处理。该日志结构不仅服务于前端可视化，也支持后续对工具可靠性、耗时分布和失败原因的统计分析。

4.3.3结构化评审与回退控制
Check模块将用户目标、计划步骤、工具轨迹、检索证据和候选答案进行语义聚合，并生成CheckOutput。判断规则包括目标完成度、证据覆盖度、输出格式合规性、工具调用合理性和权限边界遵守情况。默认情况下，score达到80分且judge为通过时，任务进入最终输出阶段。
若校验失败，系统根据失败原因触发回退控制。证据不足时回退到检索阶段，工具参数错误时回退到Planner重新生成参数，输出格式错误时进行结构化重试，权限错误时终止或选择低权限工具。相比一次性开环输出，该闭环模式能够提高长程任务的决策韧性，并降低逻辑错误直接暴露给用户的概率。

4.4检索增强链路实现
RAG模块在技术选型上遵循“召回优先、生成兜底”的原则，在文档生命周期各阶段采用如下实现方案。
在上传与解析方面，后端接收文件后依据MIME类型分发解析器。PDF采用PyMuPDF提取文本与坐标信息，并保留页码用于溯源；Office文档通过python-docx与openpyxl解析，表格内容转换为Markdown管道符格式以维持结构；纯文本文件直接读取并进行编码归一化。解析产物经过重复内容过滤、控制字符清理和UTF-8统一编码后进入切分阶段。
切分与嵌入方面，系统采用递归字符切分策略（RecursiveCharacterTextSplitter），分隔符优先级从段落符（\n\n）、换行符（\n）、句号（。/.）到空字符逐级降低。块大小（chunk_size）设为512字符，重叠（overlap）设为64字符，用于保证跨段落语义连续性。嵌入模型选用BAAI/bge-large-zh-v1.5（1024维），通过sentence-transformers加载，向量相似度采用余弦距离（cosine similarity）。
索引与检索方面，向量索引采用pgvector扩展，向量维度为1024，相似度检索使用<=>运算符。除向量召回外，系统并行执行BM25词项匹配，基于jieba分词构建稀疏索引，默认召回Top-10。两路结果通过RRF（Reciprocal Rank Fusion）融合，k值取60，最终选取Top-5片段送入生成流程。该设计兼顾语义召回和关键词匹配，适合中文企业文档中专有名词较多、格式差异较大的场景。

4.4.1多链路召回与融合重排
在实践中，单向量召回容易出现“语义相似但事实不一致”或“技术词密集但主题不相关”等问题。为降低此类风险，Agentlz采用向量召回与BM25召回并行的多路径融合模型。向量召回负责捕捉语义近邻，BM25负责增强关键词、字段名和编号类问题的精确匹配，两路结果再通过RRF进行统一排序。
对于召回后的Top-K候选片段，系统可选用重排模型进行二次筛选。重排阶段重点评估问题与片段之间的语义相关性和证据覆盖程度，减少仅因局部词项重合而进入上下文的噪声片段。该策略能够提升中文企业文档场景下的召回稳定性，尤其适用于包含大量技术术语、表格字段和制度条款的异构文档。

4.4.2查询改写与上下文组装
为提高召回效果，系统支持在检索前对用户输入进行查询改写。查询改写将原始问题扩展为若干语义等价或互补的子查询，例如将口语化问题改写为制度条款查询，将模糊描述改写为字段名查询，将多条件问题拆分为多个检索意图。多个子查询分别召回后，系统对结果进行融合、去重和排序。
上下文组装阶段需要在证据充分性和上下文长度之间取得平衡。系统通过限制片段数量、限制总字符数和保留来源标记来控制输入规模，避免长上下文导致成本上升和注意力分散。最终注入模型的上下文包含片段内容、文档来源、页码或位置标识，使答案生成阶段能够引用具体证据。

4.4.3召回性能基线与策略对比
为验证多链路召回效果，本文在内部测试集上比较不同召回策略的命中率。测试集包含50条企业文档问答对，覆盖事实检索（40%）、数值比对（30%）和多文档综合（30%）三类问题。Top-5命中率用于衡量相关证据是否进入前五个候选片段，首条相关平均位次用于衡量证据排序质量。

表4.1召回策略对比（测试集50条）
策略	Top-5命中率	平均召回数	首条相关平均位次	备注
纯向量召回	68%	5.0	2.3	语义相近但术语不匹配时失效
纯BM25召回	54%	5.0	3.1	关键词命中强但语义泛化弱
向量+BM25融合（RRF）	82%	5.0	1.8	兼顾语义与词项匹配

表4.1显示，融合策略相比单一向量召回和单一BM25召回具有更高命中率。查询改写进一步提高了相关证据进入候选集的概率，但也带来候选冗余，因此需要去重和裁剪机制配合使用。该结果说明，多路径召回能够在企业文档问答场景中提升检索阶段的稳健性。

4.5异步任务与实时推送
针对系统吞吐与交互体验之间的矛盾，Agentlz使用消息队列将耗时任务从同步请求链路中移出。测评运行、索引构建、大文件解析和长工具调用等任务均可作为后台任务执行，主接口只负责创建任务记录、返回任务ID并启动状态订阅。后台消费者执行任务时持续更新进度，并通过WebSocket或SSE向前端推送阶段事件。
在评测场景中，一个任务通常包含多个样例，若全部同步执行，接口容易超时且用户无法感知进度。系统采用“分批执行+结果聚合”的策略：后端创建评测运行记录，记录total_count、completed_count和状态信息，并投递MQ消息；消费者按batch_size拉取样例切片执行，每完成一条即写入聚合结果并推送item_done事件；若任务尚未完成，则发布下一批MQ消息继续执行；全部完成后写入finished_at并推送done事件。
该策略将长任务拆解为多个可控短任务单元，提高了失败恢复和状态回放能力。若某一批次失败，系统可以根据任务ID重新投递，避免整个任务从头执行。前端则可以持续展示进度、单条结果和错误提示，降低长时间等待带来的不确定性。

4.6前端实现
React-Admin通过声明式数据提供者和权限控制，为后台管理系统提供了可复用的页面组织模式[8]，该模式也符合React生态中声明式编程和组件复用的基本思想[9]。Agentlz前端基于React-Admin组织页面、资源和数据源调用，实现用户与租户管理、鉴权登录、智能体配置与运行入口、文档上传与RAG管理、评测数据集管理、评测启动、结果回放、WebSocket连接监控和运行状态展示等能力。
前后端联调以Axios为基础实现统一httpClient，并按领域封装evaluation、rag、agent、mcp等API模块。页面组件只负责交互状态和展示逻辑，不直接拼装底层请求。该组织方式可以在接口变更时集中修改调用层，降低维护成本。对于流式任务，前端根据SSE事件类型更新链路面板；对于异步任务，前端通过WebSocket订阅任务Topic并更新进度条、日志列表和结果表格。
在交互设计上，前端强调过程可见性。智能体运行页面展示计划步骤、工具调用状态、检索片段、校验评分和最终答案；评测页面展示样例执行状态、成功率统计和失败原因；文档页面展示上传、扫描、解析、切分和索引状态。通过把后端结构化轨迹转化为可视化事件，用户能够更直观地理解智能体的执行过程。

5  实验设计与评测
5.1任务集设计
实验任务集围绕“检索-工具-多步执行”的典型链路构建，覆盖信息检索问答、复杂任务分解、跨模块协作和工程能力验证等场景。信息检索问答任务基于上传文档进行事实性问答、数值查找和来源引用，用于检验RAG链路的召回质量和答案可追溯性。复杂任务分解任务要求系统将自然语言目标拆成多个步骤，并按照计划执行和校验，用于检验Planner-Executor-Check工作流的稳定性。
跨模块协作任务结合检索、工具调用和结果校验，用于评估闭环机制在多来源信息整合中的有效性。工程能力任务包括文件上传与解析、评测任务分批执行、实时推送和权限触发，用于检验系统在非理想环境下的可用性和恢复能力。任务集设计不追求覆盖所有智能体应用，而是聚焦企业知识处理和受控工具执行中最常见的风险点。

5.2评测指标
指标体系从准确性、效率、可解释性、鲁棒性和安全性五个维度衡量。准确性与任务成功率用于判断最终输出是否满足目标；效率指标包括平均步数、平均耗时和可选的token或调用成本；可解释性指标关注轨迹是否完整、是否可回放、关键结论是否有证据支撑；鲁棒性指标关注检索噪声、工具失败和网络波动下的恢复能力；安全性指标关注是否存在越权访问、敏感信息泄露和不当工具调用。
对于检索问答任务，额外统计引用命中率和证据覆盖率。引用命中率衡量回答中是否包含来源片段，证据覆盖率衡量关键结论是否能够在召回片段中找到对应依据。对于多步工具任务，额外统计工具失败率、回退次数和校验通过率。通过这些指标，可以同时观察最终结果质量和执行过程质量，避免只根据答案表面正确性评价系统。

5.3对比基线与消融设置
为分析各模块贡献，实验设置多组对比基线。第一类为无检索与有检索对比，用于评估RAG对事实问答和引用溯源的影响。第二类为CoT、Plan-then-Act和Planner-Executor-Check闭环对比，用于评估显式计划和结构化校验对多步任务的影响。第三类为无记忆、仅轨迹记录和轨迹+校验对比，用于分析过程记录和反思机制的作用。
消融实验分别去除或替换计划模块、检索模块、校验模块和反思回退模块。去除计划模块后，系统直接调用模型生成答案或工具参数；去除检索模块后，系统只能依赖模型内部知识；去除校验模块后，系统不再对目标完成度和证据覆盖进行判断；去除反思回退后，校验失败不触发重新规划。通过这些设置，可以判断各模块是否确实提升系统性能，而不是仅增加工程复杂度。

5.4实验环境与实现细节
为保证可复现性，实验记录运行环境、模型配置、检索参数和评测脚本输入输出约定。后端服务基于Python运行环境，采用FastAPI框架对外提供/v1API；前端采用React和React-Admin实现管理控制台；链式工作流通过SSE推送过程事件；异步任务通过消息队列消费，并使用WebSocket推送进度。
Agent逻辑层由Planner、Executor和Check三组提示词模板构成，每组模板均绑定对应PydanticSchema，用于约束输入输出结构。检索层采用BAAI/bge-large-zh-v1.5作为嵌入模型，向量维度为1024，相似度度量为余弦距离；Top-K参数、RRF的k值、是否启用重排、是否启用查询改写等配置均记录在实验配置中。该记录方式不仅用于复现实验，也为后续性能调优提供可观测依据。
评测数据集采用类Alpaca结构组织，核心字段包括instruction、input、fact_output和metadata。对于Markdown、纯文本或表格等非标准数据，系统先通过转换适配器将其映射为统一样例格式，再进入评测流程。这样可以保证不同来源数据在评测时具有一致的输入结构和结果对齐规则，减少因数据格式差异造成的统计偏差。

5.5结果展示方式与统计口径
由于不同任务对“正确性”的定义不同，本文采用“定量+定性”的方式展示结果，并统一统计口径。定量结果按任务场景统计成功率、平均步数、平均耗时、工具失败率和校验通过率。对于检索问答场景，额外统计引用命中率和证据覆盖率；对于多步任务，额外统计回退次数和失败恢复成功率。
定性结果选取2—3条代表性轨迹，展示Planner计划、Executor工具调用序列、Check评分与理由以及最终输出。定性分析重点讨论失败发生在哪个阶段、是否可以通过回退重新规划修复、修复成本是多少、额外调用是否带来明显收益。通过定量统计和轨迹案例结合，可以更全面地评价闭环系统的实际效果。

5.6典型失败类型与案例分析
结合原型系统的执行轨迹与日志，失败样例可以归纳为以下几类。
检索证据不足。表现为召回片段为空、相关性较弱或缺少关键事实，导致生成阶段根据不完整上下文补全答案。改进策略包括启用多链路召回、增加查询改写、提升文档切分质量、引入重排模型以及在答案生成前要求证据覆盖检查。
工具参数错误或工具不可用。表现为MCP客户端初始化失败、工具列表获取失败、工具输入输出格式不符合预期或调用超时。改进策略包括在Planner中加入工具输入Schema提示，在Executor中加入参数预校验和兜底路径，并记录失败原因用于后续工具治理。
输出格式不合规。表现为模型未按结构化格式返回计划或评审结果，导致解析失败。改进策略包括使用response_format约束输出、增强提示词中的字段说明、在解析失败时采用兜底结构继续推进，并在Check中扣分和给出修复建议。
权限边界触发。表现为跨租户访问文档、调用敏感工具或访问未授权资源被拒绝。改进策略包括在工具描述中显式声明权限边界，Planner生成计划时优先选择低权限可用工具，并将权限错误作为可恢复错误回退到Planner重选工具链。

表5.2失败类型归因与处置策略
失败类型	触发阶段	可观测信号	处置策略
召回为空	检索/执行	Top-K为空或相似度过低	查询改写+多路召回+降级总结
工具不可用	执行	client_init/get_tools异常	记录错误+回退重选工具

5.7系统测试与可用性验证
为了验证原型系统的工程可用性，本文采用“分层测试+场景回归”的方法组织测试。接口可用性测试以最小闭环通信链路为基础，覆盖租户鉴权、Header解析、SSE流式通信、WebSocket状态推送、文档上传、RAG检索、评测任务创建和结果查询等流程。测试不仅关注接口是否连通，还关注响应结构是否稳定、错误信息是否可定位、分页筛选和排序是否符合预期。
链路回归测试重点验证Planner-Executor-Check链路。相同输入在相同配置下应产生结构一致的计划和可解释评审输出；工具不可用或检索无结果时，系统应返回明确错误与降级结果，而不是崩溃或无响应。对于异步任务，测试关注状态机是否从pending进入running，再进入done或failed，避免出现中间状态悬挂。
数据一致性测试关注评测任务的“分批执行+结果聚合”链路。completed_count应单调递增且不超过total_count；content_json条目数量应与completed_count对齐；任务结束后状态应进入done或failed，并写入完成时间。前后端联调验证通过页面操作测评、文档和智能体运行流程，检查表格渲染、进度展示、错误提示和结果回放是否完整。与纯轮询模式相比，SSE和WebSocket推送模式能够降低用户等待感，并提升用户对执行过程的理解。

6  测试案例与分析
6.1企业知识检索与问答
企业知识检索与问答案例用于验证系统对私有文档的解析、索引、召回和答案生成能力。用户上传制度文件、产品说明或技术文档后，系统完成解析、切分、嵌入和索引构建。问答阶段，系统根据用户问题进行查询改写和多路召回，选择相关证据片段注入模型，并在最终回答中保留来源标记。
该案例的重点在于减少幻觉并提高可解释性。对于事实性问题，答案应直接由召回片段支撑；对于数值比对问题，系统需要同时保留多个证据片段并说明比较依据；对于多文档综合问题，系统需要标明不同结论来自哪些文档。通过前端轨迹面板，用户可以查看召回片段、相似度排序和最终引用，从而判断答案是否可信。

6.2测评系统与可回放轨迹
测评系统用于比较不同Agent版本、提示词配置和检索策略的效果。系统支持保存Agent版本快照、创建评测数据集、启动异步评测任务、实时推送进度和回放历史结果。每条样例的执行轨迹包括计划、工具调用、检索证据、校验评分和最终输出，便于进行错误分析和版本回归。
可回放轨迹使评测不再只依赖最终分数。对于失败样例，可以定位是问题理解错误、检索证据不足、工具调用失败还是校验标准过严。对于成功样例，也可以分析是否存在过多无效步骤或不必要工具调用。该能力有助于在系统迭代过程中发现提示词、工具和检索策略的具体薄弱点。

6.3大文件上传与安全治理
面向工程落地，系统提供小文件直传和大文件分片上传能力，并引入病毒查杀、一致性校验和隔离区（quarantine）策略，避免恶意文件直接进入解析与索引流程。文件上传与解析属于高风险链路：一方面，大文件若全部经由后端转发会造成带宽和存储压力；另一方面，文件内容可能包含恶意载荷或敏感信息，若未经扫描就进入解析流程，会带来安全隐患。
Agentlz将上传链路划分为两条策略路径。小文件走简单上传，由后端接收文件并写入对象存储，随后触发扫描任务；扫描通过后进入文档解析和向量化流程。该路径实现成本低，适合交互式上传和小规模文档管理。大文件走“分片上传+断点续传+前端直传对象存储”路径，前端通过后端获取分片预签名上传URL，将分片直接上传至对象存储，后端仅负责签名、状态机管理和完成确认，从而避免主服务带宽瓶颈。
完整性校验通过文件hash、分片etag和part_hash实现。若网络中断或页面刷新，前端可以根据已上传分片列表继续上传剩余部分，减少失败重传成本。上传完成后，系统先将文件置于quarantine前缀并触发扫描，只有scan_status==passed的文件才能转入可解析区域。上传、扫描、解析和索引状态均被显式建模并写入操作日志，便于后续安全审计和问题取证。多租户隔离确保不同租户文件不可互见，降低数据泄露风险。

6.4流式链路的可视化执行
针对大模型交互过程难以理解的问题，Agentlz将传统“一问一答”形式扩展为可见、可审计的链式执行视图。系统通过SSE流式接口将Planner规划步骤、Executor工具调用步骤和Check校验步骤实时推送给前端，前端根据事件类型渲染不同视图，例如计划列表、工具调用卡片、检索证据面板、评分理由和最终答案。
该案例的工程特点是“状态”和“内容”解耦。chain.step事件只表达阶段状态变化，planner.plan事件表达结构化计划，call.start和call.end事件表达工具调用生命周期，check.summary事件表达校验结论。前端可以按事件类型局部更新页面，无需等待最终响应完成。对于用户而言，这种可视化过程能够降低长任务等待焦虑；对于开发和运维人员而言，链路事件能够直接用于排查执行异常。

6.5测评任务的异步执行与结果回放
本案例展示系统对某个Agent版本进行评测的完整流程。用户选择测试集、测试目标Agent和评测配置后，调用启动接口；后端创建评测运行记录，返回eva_content_id和eva_version_id，用于标识本次评测运行和版本快照；随后后端发送消息队列任务，由后台消费者批量执行样例。
进度推送阶段，消费者每处理一条样例即更新completed_count，并通过WebSocket推送item_done事件。前端根据事件更新进度条、单条结果和失败原因。全部样例完成后，系统推送done事件并写入finished_at。若某条样例失败，系统记录失败阶段、异常类型和可恢复建议，不影响其他样例继续执行。
结果回放阶段，用户可以按agent_id查询版本列表和历史评测记录，并查看某次eva_content的content_json聚合结果。回放内容包括原始输入、标准输出、模型输出、计划步骤、工具调用、检索证据、校验评分和错误信息。该流程实现了“可回放、可对比、可追踪”的评测闭环，便于对不同提示词、模型和检索策略进行长期回归分析。

7  讨论与展望
7.1局限性
本文提出的Agentlz原型系统仍存在若干局限。第一，模型能力边界依然存在。在高不确定任务中，LLM可能生成错误计划、遗漏隐含约束或对工具结果进行错误解释，闭环校验只能降低风险，不能完全消除模型幻觉。第二，检索质量对最终效果影响显著。文档解析、切分策略、嵌入模型和召回参数都会影响证据覆盖，低质量文档或结构复杂表格仍可能导致召回不足。
第三，工具生态复杂度较高。外部工具的可获得性、权限配置、响应格式和失败模式差异较大，统一适配和治理需要持续维护。第四，评测基准仍有不足。通用评测集难以覆盖企业特定流程、私有文档分布和真实权限约束，内部测试集规模也需要进一步扩大。第五，闭环机制会增加执行步数和系统延迟，在实时性要求极高的场景中需要根据任务类型进行策略裁剪。

7.2安全与伦理
LLM智能体系统具备调用外部工具和处理私有数据的能力，因此必须在权限管理、敏感内容拦截、审计日志和失败回滚等方面建立治理机制。系统应遵循最小权限原则，只向智能体暴露完成任务所需的工具和数据范围；对于敏感文件、个人信息和高风险操作，应设置显式权限校验和操作留痕；对于模型生成内容，应通过证据引用和校验机制降低误导性输出风险。
在伦理层面，智能体系统需要明确责任边界。系统输出不能替代人工在高风险业务中的最终判断，尤其在法律、医疗、金融和安全生产等领域，应将智能体定位为辅助工具而非自动决策主体。对于失败、越权和异常调用，系统应提供可追溯记录，使责任分析和问题修复具备事实依据。

7.3未来工作
未来工作可以从四个方向展开。第一，引入更强的长期记忆与反思学习机制，使系统能够根据历史任务积累工具选择偏好和失败恢复经验。第二，结合强化学习或偏好优化方法，提升Planner的工具选择能力和Check的评审一致性，减少对手工阈值和提示词规则的依赖。第三，构建更标准化的评测基准和自动化回归体系，覆盖更多企业流程、文档类型和权限场景。
第四，进一步探索云原生部署和多智能体协作。云原生架构通过容器化、微服务、Serverless和DevOps等技术手段，将弹性、韧性、安全和可观测性等非功能能力交由基础设施承载[10]，能够为智能体系统的规模化部署提供支撑。在此基础上，可以探索受控多Agent协作和跨系统编排，但仍需要保留可审计轨迹、权限边界和失败恢复机制，以避免复杂协作带来的不可控风险。

结论
面向LLM智能体工程化落地中的黑盒执行、检索不足、工具调用不稳定和审计困难等问题，本文设计并实现了Agentlz原型系统。该系统将规划、检索、行动、记忆和反思过程显式化，并通过Planner-Executor-Check三段链式工作流对任务分解、工具调用和结果校验进行结构化约束，使语言模型的执行过程具备更强的可解释性、可追溯性和可恢复性。
实验与案例验证表明，Planner-Executor-Check工作流能够在多步任务中降低单步错误扩散风险；工具路由与RAG结合能够弥补模型无法实时获取私有知识的不足，减少事实幻觉并保留答案与证据之间的回溯链条；WebSocket、SSE和消息队列能够改善长任务场景下的交互体验和系统吞吐能力；多租户鉴权和结构化轨迹记录则为企业级部署中的权限治理和合规审计提供了基础。
总体而言，Agentlz并非追求无限开放的通用智能体框架，而是面向企业知识问答和受控多步执行任务提供一种可运行、可评测、可审计的闭环参考架构。该架构在提高任务成功率的同时，也为工业级智能体平台的工程实现提供了可复用的方法和系统设计经验。
