## 输出格式

直接修改 ，`。在每段的 `sectionContentList` 行之后插入一行：

```
        "sectionContentList": ["……原文……\n"],
        "revisedContent": ["……改写后……\n"],
  
```

- `revisedContent` 是字符串数组，与 `sectionContentList` 元素一一对应（多数段是1个，少数段是2个）
- 字符串结尾保留 `\n`，与原文格式一致
- 标点用全角（。，；："），与原文一致

## 改写硬性规则（必须遵守）

### 0 注意，如果有 [1]这种标记的句子，是间接论文引用，不要做aigc改动。

仅约束**中文字与英文字母**之间的空格，不约束中文与数字之间。

### 规则2 禁用第一人称复数和自指词

## 改写软性指南（风格方向）

PaperPass 判高的根本原因不是某些词没换，是**全篇句式骨架"过于工整"**。改写要做的就是打散这种工整，让段落带上人写论文时那种不完全对称的痕迹。

### 主要问题与改写方向

1. **句式骨架太规整**——原文常见"X是什么/Y负责什么/Z用于什么/因此有什么价值"模板  
   → 用判断句、顿挫、引述、举例错开节奏，不要让每句的结构都一样

2. **并列枚举太密**——全文"系统"出现92次、"通过"57次、"链路"33次、"结构化"21次、"能力"22次，"包括/负责/用于/支持/提供/实现"等功能动词堆叠像AI  
   → 替换为更具体的动词或代指（"它""这块""那一层"），避免反复堆"系统"

3. **综述段最像模板**——"ReAct 通过……；Chain-of-Thought……；AutoGen……；LangChain……" 这种"A方法做了什么，B方法做了什么"句式直接到 99.84  
   → 每个方法换一种句式，不要让多个方法被拉成统一节奏

4. **段落过于完整**——每段"起句定义、中间解释、末句总结价值"的完美小结，太平滑反像统一生成  
   → 加入不完全对称、局部补充、轻微重复，偶尔用破折号或反问，留一点真实写作的毛刺

5. **技术段像配置清单**——FastAPI、SQLAlchemy、WebSocket、Redis、pgvector、BM25、RRF、chunk_size、overlap 这类"组件+功能"罗列  
   → 加入"为什么这么选""调试时遇到什么""最终保留了什么取舍"，让它像工程笔记而不是架构介绍

6. **结论/伦理/未来工作太通用**——"应遵循最小权限原则""不能替代人工判断""未来工作可以从三方面推进"这种通用论文话术，分数都在 95+  
   → 用具体场景代替原则话术，比如"在X场景下看到Y"，避免空泛口号

### 参考样例的启示

`降ai参考样例.txt` 里的有效点不是用更高级的词，而是更不规整：
- 重复"以创新为先导"
- 使用"推陈出新、行之有效、市场风云变幻、游刃有余"等表达
- 句子不走"原因-措施-结果"标准结构

**借鉴打散节奏和作者式表达，但不要照搬它的口语化程度——本文是论文，要保持学术语体。**

### 推荐改写口径样例

改写目标不是把论文写成口头复盘，而是在论文语体中加入适量工程化判断，并打散过于整齐的句式。句子可以长短不一，局部可以有停顿和补充，但不要使用"说白了""动不动""谁的锅""老老实实"这类口语词。

推荐风格示例：

> 大语言模型进入业务系统后，角色已经不太像早期的问答或文本生成工具。很多场景里，它被放在一条更长的任务流中：用户目标需要先被解释，知识来源要临时选择，工具参数也常常要由模型参与组织；外部系统返回结果以后，后续输出还可能继续调整。ReAct等智能体范式正是沿着这一思路展开，把推理、检索、工具调用和观察反馈放在同一过程中交替推进。只是到原型开发和联调阶段，问题很快会从"模型答得是否正确"转向更细的工程环节。一次检索没有命中，某个参数字段遗漏，长上下文里关键事实被压到不显眼的位置，或者权限判断晚了一步，最后都可能表现为一段看似完整、实际难以信任的回答。对企业知识问答和多步任务来说，答案本身只是结果；来源是否清楚、过程能否回放、失败原因能否定位、权限依据是否明确，才决定这类系统能不能真正落地。

## 其他执行约定

1. **保留事实**：参考文献编号 [1][3][6]、图表号、表号、关键术语（Planner、Executor、Check、FastAPI、ToolCall、CheckOutput、WorkflowPlan 等专有名词）不能改名，参考文献这段也不要做aigc改动。
2. **字数控制**：改写后字数与原文相近（±20% 以内），不大幅压缩或扩展
3. **逐段处理**：一次只改一段，避免上下文串味
4. **JSON 合法性**：改完一批后跑一次验证：
   ```bash
   node -e "const t=require('fs').readFileSync('检测报告_163909.txt','utf8');const m=t.match(/var data = (\{[\s\S]*\});\s*$/);const d=JSON.parse(m[1]);console.log(Object.keys(d).length,Object.keys(d).filter(k=>d[k].revisedContent).length);"
   ```
