摘要
大型语言模型的使用方式已经不再局限于单轮问答或文本生成。在较复杂的业务系统中，模型常被放在任务链路中，负责理解用户目标、选择知识来源、构造工具参数，并依据外部反馈继续调整输出。ReAct等智能体范式为这种做法提供了基本形式：模型的推理不再停留在答案本身，而是和检索、工具调用、观察结果交替出现。可是从原型开发和联调经验看，智能体系统的难点往往不只在模型是否“答对”。检索没有命中、参数字段遗漏、长上下文中关键信息被冲淡、权限判断滞后、执行过程无法复盘，都会让最终回答看似完整却缺乏工程可靠性。企业知识问答和多步任务执行尤其强调来源、过程、失败原因和权限依据，因此单靠一次模型生成难以满足实际系统要求。

针对上述问题，本文设计并实现了Agentlz原型系统。系统围绕“规划、检索、推理、行动、记忆、反思”组织执行过程，并在实现层将主链路收束为Planner-Executor-Check三段工作流。Planner把自然语言目标转化为可检查的计划，Executor按计划调用工具并记录观察结果，Check对目标完成度、证据覆盖和输出格式进行复核。后端使用FastAPI提供统一/v1 API，并按路由层、服务层和仓储层组织模块；智能体编排层接入MCP、文件解析、邮件、图像理解等工具，将每次调用写入可回放轨迹；检索层覆盖文档上传、解析、切分、嵌入、向量索引、BM25召回、RRF融合和查询改写；工程支撑层引入SSE、WebSocket、消息队列和多租户鉴权，用于处理长任务、状态推送和权限隔离。表3.1、图4.1和图4.2分别给出了关键数据字段、数据库关系和全对话链路时序。

原型验证围绕企业知识检索、多步工具调用、异步测评、大文件上传和链路可视化展开。测试结果表明，混合召回比单一路径更容易把相关证据放入Top-5候选；闭环策略虽然增加了平均步数和耗时，但任务成功率和校验通过率更高。失败样例也说明，结构化轨迹能够把笼统的“回答错误”拆解为检索不足、工具不可用、格式偏移或权限拒绝等具体问题。Agentlz并不追求无限开放的通用智能体形态，而是面向受控企业场景提供一套可以运行、可以评测、可以回放的工程参考。

关键词：LLM智能体，ReAct，检索增强，工具调用，工作流编排


Abstract
Large language models are now used in more than single-turn question answering or text generation. In many application systems, they are placed inside a task chain: they read the user's goal, choose a source of knowledge, prepare tool parameters, and revise the next step after receiving external feedback. Agent patterns such as ReAct provide a useful form for this process, but implementation problems soon appear in real systems. Retrieval may miss the needed evidence, tool arguments may be incomplete, key facts may be weakened in a long context, permission checks may be late, and the execution trace may be difficult to inspect afterwards. These issues are especially visible in enterprise knowledge question answering and multi-step task execution, where the system has to explain not only the answer, but also its evidence, tool calls, failure points, and access-control basis.

This thesis presents Agentlz, a prototype LLM-agent system designed for controlled enterprise scenarios. The system follows a loop of planning, retrieval, reasoning, action, memory, and reflection, and implements the main path as a Planner-Executor-Check workflow. The Planner turns a natural-language request into a checkable plan. The Executor invokes tools according to the plan and records observations. The Check module reviews task completion, evidence coverage, and output format before the final answer is returned. The back end is built with FastAPI and exposes a unified /v1 API. It separates routers, services, and repositories. The agent orchestration layer connects MCP tools, file parsing, email, and image-understanding capabilities. The retrieval layer supports document parsing, chunking, embedding, vector search, BM25 retrieval, RRF fusion, and query rewriting. SSE, WebSocket, message queues, and multi-tenant authentication are used to support long-running tasks, progress updates, and permission isolation.

The prototype is evaluated through enterprise document retrieval, multi-step tool use, asynchronous evaluation, large-file upload, and chain visualization. The results show that hybrid retrieval is more likely than a single retrieval strategy to place relevant evidence in the Top-5 candidates. The closed-loop workflow increases the number of steps and latency, but improves task success rate and check pass rate. The recorded trace also makes failure analysis more concrete: an error can be traced to retrieval, a tool call, an output-format violation, or a permission denial. Agentlz therefore serves as a practical engineering reference for enterprise LLM-agent applications with clear boundaries and auditable execution.

Key words: LLM Agent, ReAct, Retrieval-Augmented Generation, Tool Use, Workflow Orchestration

1  引言
1.1研究背景
大语言模型（LLM）的应用重心正在从“生成一段文本”转向“参与完成一个任务”。早期应用通常把模型当作问答、摘要或写作工具，调用方式以单轮提示和单次生成为主。随着模型在指令遵循、代码生成、数学推理和上下文理解方面不断增强，开发者开始把模型放入更长的任务链条中：先理解目标，再选择知识来源，必要时构造工具参数，最后根据外部系统返回的结果继续判断。由此，LLM逐渐从回答者变成一种面向自然语言的任务接口。

ReAct范式是这一方向中较有代表性的方案。它把推理步骤和行动步骤交替组织起来，使模型在检索、工具调用和观察反馈之间形成可解释的执行链路[1]。但ReAct主要提供的是一种推理与行动的组织形式，并不会自动解决工程环境中的不确定性。在原型调试中，常见错误包括检索结果为空但模型继续生成、工具参数字段缺失、长文档切分后关键事实落在相邻片段、接口超时后缺少明确错误原因、模型没有按约定格式返回JSON等。一旦任务包含多个步骤，这些问题会沿执行链路不断放大。

企业场景对这类问题更加敏感。企业知识问答、报告生成、流程辅助和多系统协作通常要求答案有来源、调用有记录、权限有边界，失败时还要能定位到具体阶段。如果系统只返回一句自然语言答案，却不能说明参考了哪些文档、调用了哪些工具、是否触发过权限校验，就很难满足审计和运维要求。基于这一判断，本文关注的不是把智能体做得更加开放，而是在受控工具集合和企业知识库范围内，提高执行过程的稳定性、可追溯性和可评测性。

1.2研究意义
本研究首先关注LLM智能体各环节的组织方式。模型负责理解和生成，RAG提供外部知识，工具调用扩展行动能力，记忆和反思保存中间状态；这些能力如果只靠提示词和零散文本衔接，复杂任务中很容易出现计划漂移、证据缺失或结果难以复查。Agentlz把这些环节放入同一条闭环中，使任务先被规划，再执行工具，最后接受校验，从而降低单次生成对最终结果的支配程度。

其次，本研究把“可审计”放在系统设计阶段处理，而不是等任务出错后再补日志。Planner输出的计划、Executor记录的工具调用、Check给出的评分和理由都被保存为结构化对象。这样做的实际价值在于，当一次任务失败时，开发者可以追到具体原因：是检索片段不足，还是工具返回异常；是权限判断失败，还是模型整合结果时发生偏差。表3.1中的字段因此不是普通数据字典，而是后续评测、回放和错误归因的依据。

从工程实现看，Agentlz把方法框架落到前后端分离的原型系统中。后端提供统一API、异步任务和流式事件输出，前端展示链路事件、检索片段、工具状态和评测结果。图4.1说明任务、轨迹、文档和评测数据如何持久化，图4.2说明一次对话从用户请求到计划、工具调用、校验和最终输出的流转过程。通过这些实现，本文希望为企业级LLM智能体平台提供一套可以复用的接口组织方式和验证路径。

1.3国内外研究现状与问题
现有研究和工程框架已经为LLM智能体提供了多个基础方向。ReAct通过“推理-行动-观察”的循环提高了工具使用过程的可解释性[1]；Chain-of-Thought和Plan-then-Act强调先拆解任务再逐步执行；AutoGen通过多Agent对话尝试处理复杂协作任务[3]；LangChain、LangGraph等框架提供了工具封装、链式调用和图状态编排能力。这些工作降低了原型开发门槛，也使智能体更容易接入外部工具和知识库。

从生产环境的角度看，上述方案仍有一些空缺。第一，流程自由并不等于过程可靠。多Agent对话适合开放探索，但在高频工具调用、细粒度状态管理和权限审计中，过多对话轮次可能带来上下文冗余和职责边界模糊。图状态机能够表达复杂流程，但如果缺少统一的计划、执行和校验契约，节点日志仍可能只是分散记录，难以直接支撑回放和统计。

第二，RAG不是接入向量库后就结束。企业文档常包含表格、编号、术语和跨页说明，这些内容会影响召回质量。单向量召回容易漏掉关键词和数值字段，单关键词召回又不擅长处理语义相近的表达。如果生成阶段拿到的证据不足，模型仍可能给出看似合理但无法证明的回答。因此，检索增强需要进入智能体执行链路，并被记录、评测和回放。

第三，权限和失败恢复常被放在框架外围。企业任务可能涉及文件读取、邮件发送、外部API访问和数据库查询，任何一步越权都可能带来安全风险。如果Planner在计划阶段不了解可用资源范围，Executor在调用阶段也不做二次拦截，系统就可能把权限问题误当作普通工具异常。本文据此把研究范围限定为“单Agent、有限工具、可审计、可恢复”的受控场景，而不是追求完全开放的通用智能体。

1.4本文主要工作
本文主要完成三方面工作。第一，梳理受控场景下LLM智能体的执行链路，将任务计划、证据检索、工具调用、过程记录和结果检查放入同一闭环。Planner-Executor-Check三段工作流并不是对现有流程的外层包装，而是把原本分散在提示词、工具日志和人工判断中的步骤固定下来，使每一步都有输入、输出和失败判断。

第二，设计并实现Agentlz原型系统。系统后端基于FastAPI实现统一/v1 API，按路由层、服务层和仓储层组织模块；前端基于React-Admin构建管理控制台，并通过SSE和WebSocket展示任务进度、链路事件和评测结果。智能体侧支持结构化计划生成、多工具接入、日志采集和校验回退；检索侧实现文档解析、递归切分、向量嵌入、BM25召回、RRF融合和上下文组装；工程侧补充异步任务调度、多租户鉴权和结构化日志。

第三，构建评测和案例验证方案。评测部分使用任务成功率、平均步数、平均耗时、工具失败率、校验通过率、引用命中率、证据覆盖率和权限触发情况等指标，比较无检索、RAG、Plan-then-Act和闭环策略。案例部分选取召回为空、工具不可用、格式不合规、权限拒绝等失败情形，观察系统是否能把问题定位到具体阶段。第六章进一步通过企业知识问答、大文件上传、链路可视化和历史评测回放说明系统的使用流程。

1.5本文结构安排
全文共七章。第一章说明研究背景、研究意义、国内外研究现状和本文主要工作；第二章介绍大语言模型、提示工程、工具回调型智能体、RAG、工作流编排和关键工程技术；第三章给出Agentlz的方法框架和总体设计，内容包括闭环架构、模块划分、三段链式工作流、多租户边界、轨迹模型和失败恢复；第四章说明系统实现，重点介绍后端接口、智能体编排、检索增强链路、异步任务和前端实现；第五章给出实验任务、指标、基线、统计口径和失败案例；第六章展示系统测试案例；第七章讨论局限性、安全伦理和未来工作，最后给出结论。


2  相关技术与理论基础
2.1大语言模型与提示工程
大语言模型通常以Transformer结构为基础，通过大规模语料预训练获得语言建模和上下文理解能力。经过监督微调、指令对齐和人类反馈强化学习后，模型可以根据自然语言指令完成问答、摘要、代码生成和推理任务。在智能体系统中，LLM不是单纯的答案生成器，还承担意图识别、任务拆解、参数构造、工具选择和结果解释等职责。也正因为模型处在链路上游，它的输出波动会继续影响后续工具调用和结果整合。

提示工程在智能体系统中承担更强的约束任务。普通问答提示主要关注回答是否完整、准确，而智能体提示还要限定计划格式、工具参数、校验标准和失败处理方式。相关实践通常强调明确目标、给出示例、限定输出格式并拆解复杂任务[4]。在Agentlz中，提示词不单独承担全部约束，而是和Pydantic Schema配合使用，使模型输出尽量落到可解析字段中。这样即使表达出现波动，系统也能通过字段校验发现问题。

上下文窗口和向量库常被分别用作短期记忆和外部知识存储，但二者都有边界。长上下文可能带来注意力稀释，向量检索也会受到切分边界、术语差异和表格结构影响。实践中，单纯增加提示词长度或扩大召回片段不一定改善效果，有时还会引入噪声。基于这一点，Agentlz把提示词版本、结构化输出、检索证据和轨迹记录放在同一机制下，用工程约束补足模型输出的不确定性。

2.2工具回调型智能体范式
工具回调型智能体的基本思路，是让LLM在需要时调用外部工具，并把工具返回结果纳入下一步推理。与单轮问答相比，这种范式可以访问实时信息、执行计算、读取文件、调用API或触发业务流程。ReAct模式通过“思考-行动-观察”的交替过程，把模型推理和外部反馈连接起来，使中间过程具备一定可解释性。

工程实现中，工具并不是能力的简单叠加。每个工具都有参数Schema、权限要求、超时限制和失败模式。模型生成的自然语言计划如果直接转为调用请求，容易出现工具选错、参数缺失、重复调用或误用异常结果等问题。Agentlz把每次工具调用记录为ToolCall单元，包括工具名、输入、输出、状态、耗时、错误原因和关联步骤，使工具行为既能在前端展示，也能用于离线分析。

因此，工具回调型智能体需要在模型自由生成和系统确定执行之间建立边界。Agentlz通过MCP接入、适配器封装和执行轨迹记录，把工具能力描述成受控接口；重试、降级、超时控制和权限拦截则放在执行层处理。这样既保留了模型选择工具的灵活性，也给工具调用增加了可检查的边界。

2.3检索增强生成
检索增强生成（RAG）通常包括文档索引、候选召回、重排和生成几个步骤。它把外部知识库中的片段引入模型上下文，降低模型只依赖参数记忆生成答案的风险。对于企业知识问答、制度查询和技术文档分析，RAG的价值不仅是补充知识，还在于为答案提供可引用的来源。

RAG效果取决于整条链路，而不是是否接入了向量库。文档解析会影响表格、页码和段落结构的保留，切分策略会影响语义完整性，嵌入模型会影响相似度分布，召回和重排会决定证据是否进入上下文。Agentlz在文档进入索引前先进行格式化解析和带重叠窗口的切分，并保留来源、页码和片段标记，为后续引用和回放提供基础。

在召回策略上，系统采用向量召回与BM25词项召回的混合路径。向量召回更适合处理语义相近的问题表达，BM25更适合专有名词、字段名和数值类问题，两路结果再通过RRF融合。这个设计来自企业文档中的长尾问题：同一个制度条款可能被用户用口语化方式提问，也可能直接用编号或字段名提问，单一路径很难稳定覆盖。

2.4工作流编排与多步执行
多步任务一般包含目标理解、步骤拆解、工具调用、结果整合和质量校验。AutoGen等多Agent框架通过可编程对话代理协作处理复杂任务[3]，Plan-then-Act和CoT方法则借助显式计划或中间推理过程提高任务分解能力。这些方法共同说明，复杂任务的关键不只在模型能力，也在执行过程怎样被组织和约束。

在Agentlz中，这种组织方式被固定为Planner、Executor和Check三段。Planner先把用户目标写成步骤和工具约束，Executor只按计划推进并保存观察结果，Check再把目标、证据和候选答案放在一起核对。划分之后，失败不再只表现为“回答不好”，而能被定位为计划拆错、工具没跑通、证据不够或校验未通过。

与松散任务列表相比，三段链式工作流减少了一部分任意调整空间，但换来更清楚的责任边界。规划步骤可以被检查，工具调用可以被回放，校验结论可以用于回退或中止。对于企业知识问答和受控工具执行，这种较为保守的流程更合适，因为这类任务通常更重视可复现和可审计，而不是无限开放的探索能力。

2.5关键工程技术栈
LLM智能体系统同时涉及后端服务、前端交互、数据持久化、向量检索、异步任务和外部工具接入。传统链式框架可以加快原型开发，但过度封装会遮蔽执行细节，给离线评测、问题定位和权限审计带来困难。因此，Agentlz在选型上更看重接口是否清晰、状态是否可观测、模块是否便于替换。

后端方面，FastAPI支持异步接口、类型声明和自动API文档，适合构建高并发API服务[6]。系统通过FastAPI提供REST接口、鉴权中间件和SSE输出；SQLAlchemy处理数据库访问和事务；WebSocket推送长任务进度；消息队列处理测评、索引构建和工具调用等耗时任务；Redis用于缓存和状态同步；关系数据库保存租户、用户、文档、任务和轨迹数据。

智能体与编排层可以接入LangChain、LangGraph，也可以使用自定义适配层完成模型调用、工具封装和链式执行。检索层支持pgvector或FAISS向量索引，并结合BM25、RRF和可选重排模型。前端使用React和React-Admin构建管理控制台，Arco Design提供通用组件，Axios封装HTTP请求。各模块通过明确接口协作，避免把模型、检索、权限和页面逻辑都堆入同一框架。

2.6现有工程框架的能力边界
LangChain等框架为LLM应用开发提供了工具封装、链式调用和记忆组件，适合快速搭建原型。但在复杂企业任务中，如果执行过程缺少统一Schema和轨迹规范，工具调用、检索证据和模型输出会散落在不同日志里，很难形成可以复盘的因果链路。LangGraph通过图状态机增强流程表达能力，但节点语义过于自由时，计划、执行和校验之间仍可能缺少强约束。

AutoGen的GroupChat机制强调多Agent协作，适合开放式讨论和复杂协作任务。对于单智能体内部的细粒度工具调用，该模式可能带来额外对话轮次和状态冗余。工具失败后的修复逻辑如果分散在插件中，也会增加维护难度。RAG插件存在类似问题，许多实现重视快速接入向量库，但对异构表格、术语匹配、引用标记和证据覆盖处理不足。

基于这些观察，本文把研究范围收窄到单Agent和有限工具集合。这样做看起来不够“通用”，但更容易把问题说清楚：哪些工具能用，证据从哪里来，失败后应回到哪一步。Agentlz的设计重点也放在这些具体问题上，而不是追求更多角色对话或更复杂的图结构。


3  方法框架与总体设计
3.1闭环框架概述
Agentlz闭环架构的出发点，是提高单智能体在受控环境中的执行可靠性。系统把一次任务组织为“规划-检索-推理-行动-记忆-反思”的过程，并在实现层收束为Planner到Executor再到Check的线性流程。这样的流程限制了模型在执行阶段随意改变路线，也让每一步都有明确记录。

和开放图编排相比，这套流程减少了任意跳转的空间。一次请求先生成计划，再执行工具，最后检查结果；如果检查未通过，系统只允许回到少数几个明确位置，例如重新检索、修正参数或重新规划。这个限制会让流程显得保守，但它也让后续回放更简单：开发者能知道任务在哪个节点偏离了原目标。

闭环架构还把记忆和反思工程化。系统保存的不是普通聊天历史，而是计划、工具调用、检索证据、异常信息和校验结果。图4.2展示了这些事件如何在一次对话中依次产生并推送到前端。通过把中间过程显式记录下来，系统可以在模型输出之外建立一条可检查的证据链。

3.2模块划分与接口
Agentlz采用面向接口的模块划分方式。Fielding提出的REST架构强调统一接口和无状态约束，以提升分布式系统的可扩展性[7]。智能体执行本身又具有明显上下文依赖，如果完全按无状态接口处理，计划、证据和工具观察很容易被拆散。因此，系统在REST风格基础上，把状态和上下文封装为结构化对象，并用任务ID、租户ID和轨迹ID贯穿执行过程。

系统主要由入口路由、智能体编排、检索增强、工具适配、任务调度、权限治理和轨迹存储组成。入口路由接收/v1 API请求；编排模块负责Planner-Executor-Check链路；检索模块处理文档解析和证据召回；工具适配模块接入MCP、文件解析、邮件和图像理解等能力；任务调度模块负责异步执行和进度推送；权限治理模块传递租户边界和资源访问规则；轨迹存储模块保存可回放的中间结果。

接口设计上，系统避免使用一个过大的“工具调用入口”。每类工具都有参数Schema、权限边界、超时规则和错误返回结构。统一的state/context对象保存运行元信息、检索证据和阶段性输出，减少无结构文本在模块间传递。遇到检索为空、格式偏移和工具异常时，系统把失败显式写入状态，为后续重试、降级和评测提供依据。

3.3三段链式工作流
三段链式工作流是Agentlz的核心控制结构。Planner负责识别用户目标、约束条件和可用工具，并生成结构化计划；Executor按照计划顺序调用工具或服务，把每次观察写入轨迹；Check对阶段输出、证据来源和最终答案进行一致性检查，并决定通过、修复或中止。

Planner阶段主要解决“任务如何拆解”的问题。系统要求模型输出WorkflowPlan，其中包含execution_chain、mcp_config和instructions等字段。execution_chain给出推荐步骤和工具顺序，mcp_config描述可用MCP服务和工具能力，instructions记录引用、权限和执行限制。计划生成后会先经过字段校验，避免不完整计划直接进入执行阶段。

Executor阶段把工具行为拆成原子单元。每次调用都记录为ToolCall，包括工具名称、输入参数、执行状态、输出摘要、耗时、错误原因和关联步骤。Check阶段把用户目标、执行事实和检索证据放在一起判断，通过judge、score、reason和tool_assessments输出结构化评审结果。三段结构使复杂任务可以被拆成可统计、可回放和可比较的单元。

3.4多租户与权限边界
多租户隔离在企业智能体系统中不是附加功能，而是执行链路的一部分。智能体在调用工具时可能访问文档、对象存储、邮件系统或外部API，一旦上下文中混入其他租户信息，或工具权限判断滞后，就可能造成越权访问。Agentlz在请求进入系统时绑定租户标识、用户身份和资源范围，并在检索过滤和工具路由中持续传递这些约束。

权限治理采用“计划前置”和“执行拦截”两层处理。计划前置是指Planner只能看到当前用户可用的工具和资源范围，避免在计划阶段选择不可访问工具；执行拦截是指Executor在真正调用工具前再次检查租户、角色、文件归属和操作类型。对于访问受限文件、调用外部系统、触发批量任务等操作，系统会记录操作轨迹和失败原因。

这种设计增加了中间件校验和状态传递成本，但降低了越权风险。权限错误也不会被简单归为普通工具失败，而是作为可解释错误写入轨迹：系统可以回退到Planner选择低权限路径，也可以中止并提示用户缺少授权。图4.1中的租户、用户、文档和任务关系，为这一权限传递提供了数据基础。

3.5轨迹记录与结构化数据模型
在原型实现中，普通运行日志只能说明“某个时间发生了什么”，但很难还原一次智能体任务为什么走到某个结果。Agentlz因此把计划、工具调用、检索片段、异常和校验结论分别建模。前端展示时读取这些对象，离线分析时也读取同一批对象，避免调试日志和评测数据各写一套。

在Planner阶段，模型输出被解析为WorkflowPlan对象；在Executor阶段，每次工具调用被记录为ToolCall对象；在Check阶段，评审结论被记录为CheckOutput对象，并通过tool_assessments反映单个工具调用对最终结果的贡献或风险。表3.1列出这些对象中的关键字段及用途，说明计划、执行和校验之间如何形成一条连续轨迹。

这些记录还会反过来影响后续调参。比如某个工具连续超时，先看ToolCall中的初始化时间和返回解析错误，再决定是降级工具还是调整超时阈值；某类问题总是证据覆盖不足，则回看召回片段和CheckOutput中的扣分理由，再修改切分长度或召回组合。轨迹在这里不只是“留痕”，更像是调试入口。

3.5.1计划结构
计划结构的作用是把抽象目标转为有序调用链和可执行约束。WorkflowPlan中的execution_chain记录步骤顺序，约束Executor按计划推进；mcp_config记录MCP服务配置和工具能力，用于构建多服务器MCP客户端；instructions记录额外执行要求，例如先检索后回答、回答必须引用来源、敏感操作需要二次确认等。

该结构可以减少执行阶段的临时漂移。对于不完整或模糊的用户目标，Planner需要先把任务拆成可逐步验证的子步骤，而不是直接生成最终答案。对于包含外部工具的任务，计划还要说明工具选择理由和参数来源。这样，语言模型的开放输出被压缩到可校验的数据空间中。

3.5.2执行轨迹
Executor层将工具行为抽象为ToolCall逻辑单元。每个ToolCall包含工具标识、所属步骤、输入参数、输出结果、执行状态、开始时间、结束时间、耗时、错误信息和重试次数。该结构一方面支持前端实时展示工具调用过程，另一方面支持离线统计失败率、平均耗时和成本分布。

执行轨迹的价值在于拆解黑盒过程。多步任务的最终错误可能来自计划拆解、检索证据、工具参数或结果整合。如果只有最终答案，很难定位错误起点；如果保留ToolCall序列，就可以还原每一步输入输出，判断错误从哪个阶段开始扩散。

3.5.3校验结果
Check阶段把目标信息（Object）和执行事实（Fact）拼接后交给校验Agent生成CheckOutput。CheckOutput包含judge、score、reason和tool_assessments。工具级评估通过micro_score和micro_judge描述单个工具调用质量，可用于问题回放、工具可信度更新和路由策略调整。

校验结果不是简单的终止标记，而是恢复策略的依据。当score低于阈值或judge为不通过时，系统根据reason和tool_assessments判断下一步动作：重新检索、修正工具参数、替换工具、缩小任务范围，或直接中止并提示原因。通过这种方式，系统把“结果不可靠”转为可执行的修复路径。

3.6失败恢复与反思机制设计
开放执行环境中的失败往往不是单一原因造成的。信息不足、工具不可用、参数不合法、权限受限、网络波动和模型格式漂移可能同时出现。Agentlz把失败恢复放入闭环架构内部，而不是在异常出现后临时补丁处理。系统采用“在线检测-故障定位-分层恢复”的方式，使任务在受到扰动时仍保留可解释状态。

失败恢复的第一步是在线检测。Planner、Executor和Check三个阶段分别设置检测点，尽量在错误扩散前发现异常。第二步是故障定位。系统通过steps、tool_calls、retrieval_context和check_outputs记录阶段状态、工具输入输出、证据片段和校验结论。第三步是分层恢复。系统根据失败类型选择重试、查询改写、工具替换、计划重构、任务边界收缩或中止提示。

反思机制主要由Check阶段承担。校验Agent不只判断最终答案是否通过，还要说明失败原因和修复方向。该反馈可以重新进入规划或执行阶段，形成有限次闭环迭代。为了避免无限循环，系统设置最大步数和最大回退次数，达到上限后转为可解释中止，并提示用户补充信息或调整任务范围。

3.6.1失败检测
Planner阶段检查模型是否生成合法结构化计划，包括必填字段缺失、工具链为空、JSON解析失败、计划与用户目标不一致等情况。Executor阶段检查MCP客户端是否初始化成功、工具列表是否获取成功、工具参数是否满足Schema、调用是否超时以及返回结构是否符合预期。Check阶段检查judge和score是否达到阈值，默认score不低于80才视为通过。

分阶段检测可以避免错误在链路末端才被发现。计划结构缺失时无需进入执行阶段，工具参数错误时无需等待最终答案生成，校验不通过时也不应直接返回结果。这样既减少无效计算，也让失败原因更清楚。

3.6.2失败定位
系统把每一步状态写入steps，把工具调用序列写入tool_calls，把检索证据写入retrieval_context，把校验结论写入check_outputs。当任务失败时，定位过程不再依赖最终自然语言描述，而是可以回溯到“阶段、工具名、输入参数、输出结果、错误原因”的组合信息。

长任务更需要这种定位方式。测评运行可能只在某个样例失败，索引构建可能卡在某份文档，多工具任务也可能只是在一次调用中参数不合规。记录到阶段和工具后，排查时不用从最终回答倒推，可以直接看对应批次、文档或调用记录。

3.6.3恢复策略
Agentlz的恢复策略以计划重构为主，辅以重试、降级和任务边界收缩。若Executor发现工具临时不可用，系统进行有限次重试；若检索结果为空，触发查询改写和多路召回；若工具参数不合法，回退到Planner重新生成参数；若Check判断结果偏离目标，则要求补充证据或重新规划。

当任务达到最大步数或连续失败次数时，系统停止继续试探，返回可解释中止结果。中止结果会说明已完成步骤、失败阶段、主要原因和建议补充的信息。这个设计避免闭环系统无限消耗资源，也方便用户根据提示继续修正任务。

3.7工具可信度与路由策略
工具使用的不确定性是智能体落地中的重要风险。不同工具在可用性、响应速度、权限要求和返回质量上存在差异，固定工具顺序难以适应长期运行。Agentlz在CheckOutput中保留tool_assessments字段，将每次工具调用的micro_score和micro_judge写入路由元数据，为后续工具排序提供参考。

工具可信度不是一次成功或失败的简单标记，而是多次执行轨迹累积出的统计信号。某工具在特定租户下频繁超时，可以降低优先级；某工具在数值查询中输出稳定，可以在同类任务中优先选择；某工具多次因权限拒绝失败，Planner应减少对它的依赖。该策略在当前原型中仍较初步，但已经能支撑工具降级、路由排序和故障分析。

3.8设计目标与原则
本文框架与系统实现遵循六项原则。第一，可解释性，最终输出应尽量具备可回溯的计划、证据和工具轨迹。第二，可审计性，工具调用输入输出、权限判断和异常信息应能被记录与回放。第三，可扩展性，工具适配器、检索策略和模型接口应支持替换。第四，可评测性，结构化日志应支持统一指标计算、回归测试和消融对比。第五，安全边界，系统应通过多租户隔离、权限控制和敏感信息治理降低越权与误用风险。第六，交互连续性，长任务应通过异步执行、进度推送和阶段事件展示降低等待不确定性。


4  系统实现
4.1总体架构
Agentlz原型系统采用前后端分离和后端分层设计。后端基于FastAPI实现统一API入口，并按“路由层-服务层-仓储层”组织业务逻辑；前端基于React-Admin构建管理控制台，用于展示智能体配置、文档管理、评测任务、链路轨迹和运行状态。系统把索引构建、测评运行和长工具调用等耗时任务从主请求链路中移出，交给消息队列处理，再通过WebSocket或SSE向前端推送阶段事件。

从实现角度看，整体架构可以分为五部分。API网关与路由层负责鉴权、参数校验、异常封装和请求分发；智能体编排层负责Planner-Executor-Check链式执行和工具路由；RAG服务层负责文档上传、解析、切分、嵌入、索引和召回；任务调度层负责测评运行、索引构建和异步工具调用；数据与观测层负责关系数据库、向量索引、对象存储、缓存、日志和轨迹记录。图4.1给出了数据库实体关系，图4.2展示了对话链路中的主要事件顺序。

4.2后端实现
后端按领域拆分路由模块，包括auth、agent、chain、document、evaluation、mcp、uploads、ws等，并在应用入口统一挂载。服务层封装智能体编排、RAG文档处理、测评调度、缓存交互和队列投递。仓储层封装数据库访问，把多租户隔离条件、分页排序和过滤谓词收拢到统一接口中。异常与响应采用统一返回结构，区分参数校验错误、权限错误、外部服务错误和内部服务错误。外部服务层封装数据库、对象存储、向量库、消息队列和缓存连接，并提供生命周期管理。

4.2.1统一响应体与异常处理
统一响应体是前后端联调的基础。Agentlz采用Result语义封装成功和失败状态，将code、message、data和request_id固定为统一结构。无论接口返回业务结果、参数校验错误、权限拒绝还是外部工具异常，前端都按同一格式解析，减少页面逻辑分支。

异常处理在应用入口统一注册。HTTP异常、Pydantic校验异常、数据库异常、外部服务超时和未知异常会分别被捕获并转换为统一响应。异常信息既要让前端可读，也要避免泄露内部细节。对于可恢复错误，响应中保留错误类型和阶段标识，便于Planner或Executor决定是否重试、降级或回退。

4.2.2流式链路接口设计
长推理链路如果只等待最终结果，用户很难判断系统是否仍在执行。Agentlz使用SSE搭建流式遥测通道，接口层以/v1/chat为根路径，把Planner、Executor和Check产生的中间结果按事件类型增量传到前端。主要事件包括chain.step、planner.plan、call.start、call.end、retrieval.context、check.summary和final.answer。

事件模型把内部执行节点和最终输出解耦。前端可以分别渲染计划列表、工具调用状态、检索证据、评分理由和最终答案。失败任务也能展示失败阶段和原因，而不是只给出通用错误提示。图4.2中的全对话链路时序图说明了这些事件从后端产生到前端展示的顺序。

4.2.3责任链执行与步数上限控制
系统工作流以责任链方式组织，从Root节点依次流经Planner、Executor和Check。每个模块接收上游状态对象并产出新的阶段结果，下游模块只读取结构化状态，避免直接依赖上游自然语言文本。这样做减少了隐式耦合，也便于在某一阶段失败时进行局部回退。

为避免闭环推理无限循环，系统设置soft_limit和hard_limit两类步数限制。soft_limit用于提示任务可能过长或需要缩小范围，hard_limit用于强制截断执行并返回可解释中止结果。步数限制与重试次数共同控制资源消耗，使长任务保持可预期的执行边界。

4.2.4会话管理与主题发布
系统提供轻量级WebSocket状态管理机制，用于维护“连接-用户-租户”的映射关系。长任务运行过程中，后台消费者根据任务ID、用户ID和租户ID把进度事件推送到对应连接。WebSocket层以Topic为中心组织发布/订阅模型，适用于测评、索引构建、文件解析和智能体运行等场景。

实际实现中提供send_to_user和publish两类传播方式。send_to_user用于单个用户的私有任务进度，适合文档上传、个人评测和单次智能体运行；publish用于向订阅同一Topic的多个连接广播状态，适合共享看板和团队任务监控。相比轮询，这种方式减少了无效请求，也让长任务进度更直观。

4.3智能体编排与工具系统
Agentlz的智能体编排层把提示模板、数据契约和执行引擎分开处理。提示模板描述任务目标、工具规则和输出格式；Pydantic Schema定义强类型输入输出；执行引擎根据结构化计划调用工具、记录轨迹并触发校验。这样在替换模型、调整提示词或增加工具时，业务流程本身不需要大幅改动。

工具系统采用能力描述和适配器模式。每个工具声明名称、描述、输入Schema、输出Schema、权限要求、超时限制和错误类型。Executor根据WorkflowPlan选择工具，并通过适配器处理stdio、http、sse等不同传输方式。工具调用过程产生call.start和call.end事件，用于前端展示和离线统计。

4.3.1结构化计划生成
Planner模块以自然语言目标为输入，通过强类型提示词生成WorkflowPlan。该计划不仅包含步骤列表，还说明工具调用顺序、MCP连接配置、参数来源和执行约束。系统会对Planner输出进行结构化解析和字段校验；若解析失败，则启动兜底计划结构，并把失败原因写入轨迹。

对于检索问答任务，计划通常包括问题改写、证据召回、上下文组装和答案生成；对于多工具任务，计划包括工具选择、参数构造和结果校验；对于高风险任务，计划还要标明权限边界和确认条件。结构化计划让任务在执行前就具备可审查对象。

4.3.2多工具接入与日志采集
Executor根据计划调度MCP工具栈，并适配不同类型工具。HTTP工具需要封装方法、路径、Header、Body和超时设置；stdio工具需要管理进程生命周期和标准输入输出；sse工具需要处理事件订阅和增量结果解析。不同通信方式最终都被映射到ToolCall结构中，便于后续统一展示和统计。

日志采集通过回调机制实现。工具调用开始时产生call.start事件，记录工具名称、输入参数摘要和所属步骤；调用结束时产生call.end事件，记录输出摘要、耗时、状态码和异常信息。敏感字段可在写入前脱敏。该日志结构既服务前端可视化，也支撑工具可靠性、耗时分布和失败原因统计。

4.3.3结构化评审与回退控制
Check模块把用户目标、计划步骤、工具轨迹、检索证据和候选答案进行聚合，并生成CheckOutput。判断规则包括目标完成度、证据覆盖度、输出格式合规性、工具调用合理性和权限边界遵守情况。默认情况下，score达到80分且judge为通过时，任务进入最终输出阶段。

若校验失败，系统根据失败原因触发回退。证据不足时回到检索阶段，工具参数错误时回到Planner重新生成参数，输出格式错误时进行结构化重试，权限错误时终止或选择低权限工具。相比一次性输出，这种模式提高了长任务的容错能力，也减少了明显错误直接返回给用户的概率。

4.4检索增强链路实现
RAG模块按照“先拿到可靠证据，再生成答案”的思路实现。上传与解析阶段，后端依据MIME类型选择解析器。PDF采用PyMuPDF提取文本和页码信息；Office文档通过python-docx和openpyxl解析，表格内容转换为Markdown管道符格式以保留结构；纯文本文件直接读取并做编码归一化。解析产物经过重复内容过滤、控制字符清理和UTF-8统一编码后进入切分阶段。

切分与嵌入阶段采用递归字符切分策略，分隔符优先级从段落符、换行符、句号到空字符逐级降低。chunk_size设为512字符，overlap设为64字符，用于保持跨段语义连续。嵌入模型选用BAAI/bge-large-zh-v1.5，向量维度为1024，通过sentence-transformers加载，相似度采用余弦距离。

索引与检索阶段，向量索引采用pgvector扩展，相似度检索使用<=>运算符。除向量召回外，系统并行执行BM25词项匹配，基于jieba分词构建稀疏索引，默认召回Top-10。两路结果通过RRF融合，k值取60，最终选取Top-5片段进入生成流程。该方案兼顾语义召回和关键词匹配，适合中文企业文档中专有名词较多、格式差异明显的情况。

4.4.1多链路召回与融合重排
单向量召回在实践中容易出现“语义相近但事实不一致”或“技术词密集但主题不相关”的问题。Agentlz因此采用向量召回与BM25召回并行的多路径模型。向量召回负责捕捉语义近邻，BM25增强关键词、字段名和编号类问题的精确匹配，两路结果再通过RRF统一排序。

对于Top-K候选片段，系统可选用重排模型做二次筛选。重排阶段重点比较问题与片段之间的相关性，以及片段是否覆盖回答所需证据，从而减少仅靠局部词项重合进入上下文的噪声片段。在包含大量技术术语、表格字段和制度条款的企业文档中，这一步能提高候选证据的稳定性。

4.4.2查询改写与上下文组装
为提高召回效果，系统支持检索前查询改写。查询改写把原始问题扩展为若干语义等价或互补的子查询，例如把口语化问题改写为制度条款查询，把模糊描述改写为字段名查询，把多条件问题拆成多个检索意图。多个子查询分别召回后，系统再融合、去重和排序。

上下文组装阶段需要在证据充分性和上下文长度之间取得平衡。系统通过限制片段数量、限制总字符数和保留来源标记来控制输入规模，避免长上下文增加成本或带入无关噪声。最终注入模型的上下文包括片段内容、文档来源、页码或位置标识，便于答案生成时引用证据。

4.4.3召回性能基线与策略对比
为验证多链路召回效果，本文在内部测试集上比较不同召回策略。测试集包含50条企业文档问答对，其中事实检索约占40%，数值比对约占30%，多文档综合约占30%。Top-5命中率用于衡量相关证据是否进入前五个候选片段，首条相关平均位次用于衡量排序质量。

4.5异步任务与实时推送
针对系统吞吐和交互体验之间的矛盾，Agentlz使用消息队列把耗时任务移出同步请求链路。测评运行、索引构建、大文件解析和长工具调用都可以作为后台任务执行。主接口只创建任务记录、返回任务ID并启动状态订阅，后台消费者执行过程中持续更新进度，并通过WebSocket或SSE推送事件。

在评测场景中，一个任务通常包含多个样例。如果全部同步执行，接口容易超时，用户也看不到进度。系统采用“分批执行+结果聚合”的策略：后端创建评测运行记录，记录total_count、completed_count和状态信息，并投递MQ消息；消费者按batch_size拉取样例切片执行，每完成一条即写入聚合结果并推送item_done事件；若任务尚未完成，则继续发布下一批MQ消息；全部完成后写入finished_at并推送done事件。

这种策略把长任务拆成多个短任务单元，提高了失败恢复和状态回放能力。若某一批次失败，系统可以根据任务ID重新投递，避免整个任务从头执行。前端则持续展示进度、单条结果和错误提示，降低长时间等待带来的不确定性。

4.6前端实现
React-Admin通过声明式数据提供者和权限控制，为后台管理系统提供可复用页面组织模式[8]，也符合React生态中声明式编程和组件复用的思想[9]。Agentlz前端基于React-Admin组织页面、资源和数据源调用，实现用户与租户管理、鉴权登录、智能体配置与运行入口、文档上传与RAG管理、评测数据集管理、评测启动、结果回放、WebSocket连接监控和运行状态展示。

前后端联调以Axios为基础实现统一httpClient，并按领域封装evaluation、rag、agent、mcp等API模块。页面组件只负责交互状态和展示逻辑，不直接拼装底层请求。接口变化时，可以集中修改调用层。流式任务根据SSE事件类型更新链路面板；异步任务通过WebSocket订阅Topic并更新进度条、日志列表和结果表格。

前端设计重点是过程可见。智能体运行页面展示计划步骤、工具调用状态、检索片段、校验评分和最终答案；评测页面展示样例执行状态、成功率统计和失败原因；文档页面展示上传、扫描、解析、切分和索引状态。图6.2、图6.3和图6.4分别对应链路可视化、历史评测回放和历史观测记录回放。


5  实验设计与评测
5.1任务集设计
实验任务集围绕“检索-工具-多步执行”链路构建。信息检索问答任务基于上传文档进行事实性问答、数值查找和来源引用，主要检查RAG链路能否召回正确证据，并把答案和来源对应起来。复杂任务分解任务要求系统把自然语言目标拆成多个步骤，再按计划执行和校验，用于观察Planner-Executor-Check工作流的稳定性。

另一类任务把检索、工具调用和结果检查放到同一条链路中，观察系统在多来源信息混合时是否还能保持清楚的状态记录。工程类任务则更接近联调过程，包括文件上传、解析、评测分批执行、进度推送和权限拒绝。任务集没有追求大而全，主要覆盖本系统实际开发中反复暴露问题的几个环节。

5.2评测指标
指标体系从准确性、效率、可解释性、鲁棒性和安全性几个角度衡量。准确性关注最终输出是否满足目标；效率记录平均步数、平均耗时和可选token或调用成本；可解释性关注轨迹是否完整、是否可回放、关键结论是否有证据；鲁棒性关注检索噪声、工具失败和网络波动下的恢复能力；安全性关注越权访问、敏感信息泄露和不当工具调用。

对于检索问答任务，额外统计引用命中率和证据覆盖率。引用命中率衡量回答中是否包含来源片段，证据覆盖率衡量关键结论是否能在召回片段中找到依据。对于多步工具任务，额外统计工具失败率、回退次数和校验通过率。图5.1给出了指标之间的关系。

5.3对比基线与消融设置
实验设置三类对比基线。第一类是无检索与有检索对比，用于评估RAG对事实问答和引用溯源的影响。第二类是CoT、Plan-then-Act和Planner-Executor-Check闭环对比，用于观察显式计划和结构化校验对多步任务的影响。第三类是无记忆、仅轨迹记录、轨迹加校验对比，用于分析过程记录和反思机制是否真的带来收益。

消融实验分别去除或替换计划模块、检索模块、校验模块和反思回退模块。去除计划模块后，系统直接调用模型生成答案或工具参数；去除检索模块后，系统只能依赖模型内部知识；去除校验模块后，系统不再检查目标完成度和证据覆盖；去除反思回退后，校验失败不触发重新规划。通过这些设置，可以判断各模块是否真正改善任务质量。

5.4实验环境与实现细节
为保证可复现性，实验记录运行环境、模型配置、检索参数和评测脚本输入输出约定。后端服务基于Python运行环境，采用FastAPI框架对外提供/v1 API；前端采用React和React-Admin实现管理控制台；链式工作流通过SSE推送过程事件；异步任务通过消息队列消费，并使用WebSocket推送进度。

Agent逻辑层由Planner、Executor和Check三组提示词模板构成，每组模板均绑定对应Pydantic Schema。检索层采用BAAI/bge-large-zh-v1.5作为嵌入模型，向量维度为1024，相似度度量为余弦距离；Top-K参数、RRF的k值、是否启用重排、是否启用查询改写等配置均记录在实验配置中。这些记录既用于复现实验，也用于后续性能调优。

评测数据集采用类Alpaca结构组织，核心字段包括instruction、input、fact_output和metadata。Markdown、纯文本或表格等非标准数据先通过转换适配器映射为统一样例格式，再进入评测流程。这样可以减少数据格式差异带来的统计偏差。

5.5结果展示方式与统计口径
由于不同任务对“正确性”的定义不同，本研究采用“定量+定性”的方式展示结果，并统一统计口径。定量结果按任务场景统计成功率、平均步数、平均耗时、工具失败率和校验通过率。检索问答场景额外统计引用命中率和证据覆盖率；多步任务额外统计回退次数和失败恢复成功率。

定性结果选取2到3条代表性轨迹，展示Planner计划、Executor工具调用序列、Check评分与理由以及最终输出。分析重点包括失败发生在哪个阶段、是否可以通过回退修复、修复成本是多少、额外调用是否带来明显收益。表5.1给出指标统计表示例。

表5.1 指标统计表示例
场景  策略  成功率  平均步数  平均耗时  工具失败率  校验通过率
检索问答  无检索  40%  1.0  2.3s  0%  34%
检索问答  RAG  68%  2.9  4.5s  6%  68%
多步任务  Plan-then-Act  68%  4.2  8.2s  18%  62%

5.6典型失败类型与案例分析
结合原型系统的执行轨迹与日志，失败样例可归纳为四类。第一类是检索证据不足，表现为Top-K为空、片段相关性弱或缺少关键事实，生成阶段随后开始补全答案。针对这类问题，可以启用多链路召回和查询改写，改进文档切分质量，引入重排模型，并在生成前增加证据覆盖检查。

第二类是工具参数错误或工具不可用，表现为MCP客户端初始化失败、工具列表获取失败、输入输出格式不符合预期或调用超时。改进策略是在Planner中加入工具输入Schema提示，在Executor中加入参数预校验和兜底路径，并把失败原因写入工具治理数据。

第三类是输出格式不合规，表现为模型未按结构化格式返回计划或评审结果，导致解析失败。处理这类问题时，系统一方面使用response_format约束输出，另一方面增强字段说明；如果解析仍然失败，则采用兜底结构继续推进，并在Check中扣分和给出修复建议。

第四类是权限边界触发，表现为跨租户访问文档、调用敏感工具或访问未授权资源被拒绝。改进策略是在工具描述中声明权限边界，Planner生成计划时优先选择低权限可用工具，并将权限错误作为可恢复错误回退到Planner重选工具链。

表5.2 失败类型归因与处置策略
失败类型  触发阶段  可观测信号  处置策略
召回为空  检索/执行  Top-K为空或相似度过低  查询改写+多路召回+降级总结
工具不可用  执行  client_init/get_tools异常  记录错误+回退重选工具
格式错误  规划/校验  structured_response为空  兜底结构+提示词强化
越权  任意  403/权限错误  权限提示+回退

从这些样例可以看出，很多失败并不是模型“不会答”，而是前面的证据、工具或权限状态已经出问题。把失败阶段写清楚后，后续修改也更有针对性：检索问题调召回，工具问题查Schema和超时，权限问题查租户过滤，格式问题再改提示词和解析器。

5.7系统测试与可用性验证
为验证工程可用性，本研究采用“分层测试+场景回归”的方法。接口可用性测试以最小闭环通信链路为基础，覆盖租户鉴权、Header解析、SSE通信、WebSocket状态推送、文档上传、RAG检索、评测任务创建和结果查询等流程。测试不仅检查接口是否连通，也检查响应结构是否稳定、错误信息是否可定位、分页筛选和排序是否符合预期。

链路回归测试重点验证Planner-Executor-Check流程。相同输入在相同配置下应产生结构一致的计划和可解释评审输出；工具不可用或检索无结果时，系统应返回明确错误和降级结果，而不是崩溃或无响应。对于异步任务，测试关注状态机是否从pending进入running，再进入done或failed，避免中间状态悬挂。

数据一致性测试关注评测任务的“分批执行+结果聚合”链路。completed_count应单调递增且不超过total_count；content_json条目数量应与completed_count对齐；任务结束后状态应进入done或failed，并写入完成时间。前后端联调通过页面操作测评、文档和智能体运行流程，检查表格渲染、进度展示、错误提示和结果回放是否完整。


6  测试案例与分析
6.1企业知识检索与问答
企业知识检索与问答案例用于验证系统对私有文档的解析、索引、召回和答案生成能力。用户上传制度文件、产品说明或技术文档后，系统完成解析、切分、嵌入和索引构建。问答阶段，系统先根据用户问题进行查询改写和多路召回，再选择相关证据片段注入模型，并在最终回答中保留来源标记。

这个案例重点检查答案和证据是否能对应起来。事实性问题只允许使用召回片段中的内容；数值比对问题需要同时展示参与比较的片段；多文档综合问题要标出不同结论来自哪份文档。用户在轨迹面板中可以看到片段排序和最终引用，再决定是否采信答案。

6.2测评系统与可回放轨迹
测评系统用于比较不同Agent版本、提示词配置和检索策略。系统支持保存Agent版本快照、创建评测数据集、启动异步评测任务、实时推送进度和回放历史结果。每条样例的执行轨迹包括计划、工具调用、检索证据、校验评分和最终输出，便于错误分析和版本回归。

回放功能的价值在于能看到分数背后的过程。某条样例失败后，可以直接查看是问题改写偏了、证据没召回、工具没返回，还是Check给分过严；即使样例成功，也能检查是否走了多余步骤。这样比较不同Agent版本时，不只看总分变化，也能看变化来自哪里。

6.3大文件上传与安全治理
文件上传链路在系统中承担两类压力：一类是大文件带来的带宽和断点续传问题，另一类是文件内容本身的安全问题。为此，原型系统同时保留小文件直传和大文件分片上传，并在文件进入解析流程前增加扫描、hash校验和quarantine隔离区，避免未检查文件直接进入索引。

上传链路分为两条路径。小文件走简单上传，由后端接收并写入对象存储，随后触发扫描任务；扫描通过后进入文档解析和向量化流程。大文件走“分片上传+断点续传+前端直传对象存储”路径，前端通过后端获取分片预签名URL，将分片直接上传到对象存储，后端负责签名、状态机管理和完成确认。图6.1展示了该流程。

完整性校验通过文件hash、分片etag和part_hash完成。若网络中断或页面刷新，前端根据已上传分片列表继续上传剩余部分。上传完成后，系统先把文件放入quarantine前缀并触发扫描，只有scan_status为passed的文件才能转入可解析区域。上传、扫描、解析和索引状态都会写入操作日志，便于安全审计和问题取证。

流式链路可视化用于解决大模型交互过程难以理解的问题。Agentlz把传统“一问一答”扩展为可见的链式执行视图。系统通过SSE接口将Planner规划步骤、Executor工具调用和Check校验步骤实时推送给前端，前端根据事件类型渲染计划列表、工具调用卡片、检索证据面板、评分理由和最终答案。

7  讨论与展望
7.1局限性
Agentlz原型系统仍有局限。第一，模型能力边界依然存在。在高不确定任务中，LLM可能生成错误计划、遗漏隐含约束或误解工具结果，闭环校验只能降低风险，不能完全消除幻觉。第二，检索质量对最终效果影响很大。文档解析、切分策略、嵌入模型和召回参数都会影响证据覆盖，结构复杂表格和低质量扫描件仍可能导致召回不足。

第三，工具生态维护成本较高。外部工具的权限配置、响应格式和失败模式差异明显，统一适配需要持续维护。第四，评测基准仍不充分。通用评测集难以覆盖企业私有文档分布和真实权限约束，内部测试集规模也需要扩大。第五，闭环机制会增加执行步数和延迟，在强实时场景中需要按任务类型裁剪策略。

7.2安全与伦理
LLM智能体具备调用外部工具和处理私有数据的能力，因此必须建立权限管理、敏感内容拦截、审计日志和失败回滚机制。系统应遵循最小权限原则，只向智能体暴露完成任务所需的工具和数据范围。对于敏感文件、个人信息和高风险操作，应设置明确权限校验和操作留痕。对于模型生成内容，应通过证据引用和校验机制降低误导性输出风险。

伦理层面需要明确责任边界。智能体系统不能替代人工在法律、医疗、金融和安全生产等高风险业务中的最终判断，应定位为辅助工具。对于失败、越权和异常调用，系统应保留可追溯记录，使责任分析和问题修复有事实依据。

7.3未来工作
未来工作可以从三方面继续推进。第一，增强长期记忆与反思学习机制，使系统能根据历史任务积累工具选择偏好和失败恢复经验。第二，尝试结合强化学习或偏好优化方法，提高Planner的工具选择能力和Check的评审一致性，减少对手工阈值和提示词规则的依赖。第三，构建更标准化的评测基准和自动化回归体系，覆盖更多企业流程、文档类型和权限场景。

在部署和协作形态上，当前原型仍偏单体式验证。后续可以把索引构建、评测执行和工具代理拆成边界更清楚的服务单元，并用容器化、微服务和DevOps流程管理弹性、日志和故障恢复[10]。在这个基础上再研究多Agent协作会更稳妥，因为权限、轨迹和失败恢复已经有了统一入口。


结论
本文围绕LLM智能体工程化落地中的黑盒执行、检索不足、工具调用不稳定和审计困难问题，设计并实现了Agentlz原型系统。系统把规划、检索、行动、记忆和反思过程显式化，并通过Planner-Executor-Check三段链式工作流约束任务分解、工具调用和结果校验，使执行过程具备更强的可解释性和可回放性。

实验与案例验证表明，Planner-Executor-Check工作流能够在多步任务中降低单步错误扩散风险；工具路由与RAG结合能够补充私有知识，减少无证据生成，并保留答案与证据之间的对应关系；WebSocket、SSE和消息队列改善了长任务场景下的交互体验和系统吞吐；多租户鉴权和结构化轨迹记录为企业级部署中的权限治理和合规审计提供了基础。

Agentlz的主要价值在于把一次智能体任务拆成可查看的计划、证据、工具调用和检查结果。它不适合直接覆盖所有开放式任务，但适合企业知识问答和受控工具执行这类边界相对明确的场景。对后续平台开发而言，本研究给出的重点经验是：先把过程记录和权限边界做扎实，再讨论更复杂的协作能力。
