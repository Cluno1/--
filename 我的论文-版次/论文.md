# 摘要

近年来，大规模预训练语言模型（Large Language Model, LLM）在理解、生成与推理方面取得显著进展，并在零样本/少样本任务中表现出较强的泛化能力。为将语言推理能力进一步延伸至“外部行动”，学术界提出了以 ReAct（Reasoning + Acting）为代表的智能体（Agent）范式，使模型能够在检索、工具调用与环境交互中形成可回溯的“推理—行动”轨迹。然而，现有 LLM Agent 在开放场景下仍面临检索不充分、工具调用不稳定、长上下文遗忘与幻觉、轨迹难以审计、失败恢复薄弱以及工程落地成本高等问题。
本研究以“规划—检索—推理—行动—记忆—反思”的闭环为核心，结合 ReAct 与检索增强（Retrieval-Augmented Generation, RAG）机制，提出一套可复用、可扩展、可评估的 LLM 智能体方法框架与前后端分离原型系统 Agentlz。系统后端采用 FastAPI 构建统一的 /v1 API 体系，基于分层结构组织路由、服务与仓储；在智能体侧实现 Planner—Executor—Check 的链式工作流，支持多源工具（MCP、文件解析、邮件、图像理解等）路由与轨迹记录；在检索侧集成向量化索引与多策略召回，提供文档上传、切分、嵌入与查询能力；在工程侧引入 WebSocket 推送、消息队列异步执行与多租户鉴权，提升系统交互体验与可运维性。通过构建代表性任务集与评测指标体系，从任务成功率、效率、可解释性、鲁棒性与安全性等维度对原型系统进行验证，并给出典型失败案例分析与改进方向。

# Abstract

In recent years, large language models (LLMs) have achieved substantial progress in language understanding, generation, and reasoning. To extend LLM capabilities from pure text generation to real-world task execution, agent paradigms such as ReAct (Reasoning + Acting) have been proposed, enabling models to interact with external tools, retrieve knowledge, and maintain interpretable reasoning-action trajectories. However, practical LLM agents still suffer from insufficient retrieval, unstable tool usage, long-context forgetting, hallucinations, limited auditability, weak failure recovery, and high engineering costs.
This thesis proposes a closed-loop LLM agent framework centered on “Planning–Retrieval–Reasoning–Acting–Memory–Reflection”, combining ReAct and Retrieval-Augmented Generation (RAG). Based on this framework, we implement Agentlz, a front-end/back-end separated prototype system. The back end is built with FastAPI and provides a unified /v1 API with layered routing, services, and repositories. On the agent side, a chained workflow of Planner–Executor–Check is implemented to support tool routing and trajectory logging. On the retrieval side, vector indexing and multi-strategy recall are integrated for document upload, chunking, embedding, and query. On the engineering side, WebSocket streaming, message-queue-based asynchronous execution, and multi-tenant authentication improve robustness and operability. We design representative tasks and evaluation metrics to validate the prototype in terms of success rate, efficiency, interpretability, robustness, and safety, and provide failure case analyses and improvement directions.
Results show that the proposed closed-loop framework improves task completion reliability and auditability; retrieval-augmented tool execution reduces hallucination risks and strengthens source traceability; workflow orchestration and asynchronous execution enhance system throughput and interaction stability. The proposed architecture and implementation offer a practical reference for building enterprise-grade LLM agent systems.

**Keywords:** LLM Agent, ReAct, Retrieval-Augmented Generation, Tool Use, Workflow Orchestration, Multi-Tenancy

# 1 引言

## 1.1 研究背景

预训练语言模型在参数规模与数据规模提升的推动下，逐步具备了更强的语言理解、生成与推理能力。与此同时，围绕检索增强、工具使用、程序执行与网页操作等“外部行动”能力的研究快速发展，使 LLM 从“文本生成器”向“可执行的智能体”演进。ReAct范式通过将推理轨迹与工具调用交替展开，使语言模型能够在与外部知识库交互过程中动态修正推理路径，从而缓解纯链式推理中的事实幻觉问题[1]。但在开放场景下，LLM-Agent往往面临信息获取不足、工具调用不稳定、长上下文遗忘与幻觉、过程不可解释、失败恢复不足以及权限边界不清等问题，限制了工程落地。

## 1.2 研究意义

本研究围绕“语言推理—外部行动—记忆与反思”的闭环机制开展工作：一方面在方法层面将规划、检索、工具路由与反思机制结构化，降低智能体在复杂任务中的不确定性；另一方面在工程层面给出前后端分离的可运行原型系统，提供接口规范、轨迹记录与评测流程，为企业知识检索、人机协作、流程自动化与合规审计等场景提供参考。

## 1.3 国内外研究现状与问题

现有研究表明，将推理过程显式化为可观察的文本轨迹，不仅提升了任务完成准确率，还增强了智能体行为的可解释性与可诊断性[1]。学术界在智能体范式、检索增强、长上下文记忆、多步规划与多智能体协同等方向已形成一定积累，但仍存在如下痛点：检索链路与推理链路解耦不足，导致“能检索但用不好”；工具选择缺乏稳定路由与失败回滚，导致“能调用但不可靠”；轨迹可解释性与审计能力不足，难以满足企业合规与责任追踪；系统化评测基准缺失，导致优化目标不清、方案难以复现。
现有主流框架在工程落地中呈现出不同的取舍倾向。AutoGen 以多智能体对话编排为核心，通过角色化代理的群聊机制实现任务分解，但其状态管理粒度较粗，对话历史膨胀后易导致上下文窗口溢出，且缺乏对单步工具调用的结构化校验与回滚能力[2]。LangGraph 基于图状态机建模控制流，支持循环与条件分支，为复杂流程提供了灵活的拓扑表达；然而其节点语义完全开放，未对"规划—执行—校验"三阶段进行强制性约束，导致在需要严格审计的企业场景中，执行轨迹难以收敛为统一的评审结构。此外，上述框架普遍假设工具调用环境为单租户或开发环境，未将多租户隔离、权限边界与失败恢复作为一等机制内建于架构层。
与上述工作不同，本文<删除>并非构建通用的多智能体对话框架或图编排引擎，而是针对"单智能体在受控工具环境下的可靠执行"这一细分场景，将 ReAct 范式与 RAG 检索链路进行垂直整合，通过强制性的 Planner—Executor—Check 三阶段契约、结构化的轨迹数据模型，以及内建的多租户与失败恢复机制，形成面向企业知识问答与流程自动化的闭环参考架构。</删除><新增>不追求构建通用的多智能体对话框架或图编排引擎，而是聚焦“单智能体在受控工具环境下的任务执行”这一场景，在 ReAct 与 RAG 基础上结合 Planner—Executor—Check 流程、结构化轨迹记录以及多租户与失败恢复机制，形成面向企业知识问答与流程自动化的原型设计方案。</新增>

# 2 相关技术与理论基础

## 2.1 大语言模型与提示工程

已有研究将智能体架构抽象为设定、记忆、规划与行动四个核心模块，其中记忆模块借鉴人类认知科学的三阶段理论（感觉记忆—短期记忆—长期记忆），短期记忆对应Transformer上下文窗口，长期记忆则依赖外部向量存储[8]。
LLM 通过自回归建模学习语言统计规律，并在指令微调与对齐训练后具备较好的指令遵循能力。提示工程通过结构化指令、约束输出格式与提供示例等方式，提升任务完成质量。在工程系统中，提示词应支持版本化与可回溯，以便评测对比与问题定位。

## 2.2 ReAct 智能体范式

ReAct 将推理（Reasoning）与行动（Acting）交替进行：模型根据当前状态生成下一步行动（如检索、调用工具、访问 API），并将行动结果反馈至上下文继续推理，从而实现多步目标达成。该范式的关键是：对行动空间进行受控建模（工具集与参数约束）、对轨迹进行记录（便于审计与复盘）、对失败进行恢复（重试、回滚、降级）。

## 2.3 检索增强生成（RAG）

RAG 通过“索引构建—召回—重排—上下文组装—生成”链路，将外部知识注入生成过程。工程实现通常包含：文档解析、切分策略、嵌入模型、向量库/倒排索引、召回与融合策略、引用标注与可追溯性机制。本文原型系统面向企业文档场景，支持文档上传、切分、嵌入与查询，并为智能体工具调用提供统一检索接口。

## 2.4 工作流编排与多步执行

Wu 等设计了以多智能体对话为核心的 AutoGen 框架，通过可定制、可对话的代理协同机制，支持大语言模型应用以分组讨论的方式完成复杂工作流[2]。相似地，OpenAI在其 API 官方指南中归纳了提示工程的关键策略，主张通过撰写明确指令、提供参考示例以及将复杂任务分解为子步骤，以优化大语言模型的输出质量与稳定性[5]。经过研究，复杂任务需要规划与分解，常见策略包括 Plan-then-Act、CoT 与工具调用链。为了降低执行不确定性，工程上常采用“规划器—执行器—校验器”的流水线：规划器生成可执行步骤，执行器进行工具调用并返回观察结果，校验器判断结果是否满足目标并给出修复建议或终止条件。

## 2.5 关键工程技术栈

当前主流工程框架提供了丰富的链式抽象与代理封装能力，支持快速组装原型系统；然而其执行过程多以黑盒方式收敛为最终文本输出，中间步骤的观测数据缺乏统一schema，难以直接用于离线评测或审计追溯[4]。为解决这一痛点,本文原型系统采用前后端分离设计，主要运用技术栈：

1. 后端：
   FastAPI通过原生异步支持与自动API文档生成，在现代Python Web框架中展现出较高的开发效率与运行时性能[6]。FastAPI 提供 REST API 与鉴权中间件；SQLAlchemy 支持持久化；WebSocket 推送运行进度；消息队列用于异步任务执行；
2. 智能体与编排：
   LangChain/LangGraph 生态用于工具封装、模型适配与链式调用；
3. 检索：
   向量索引（如 pgvector/FAISS 等）与多策略召回；
4. 前端：
   React + React-Admin 形成后台管理框架；Arco Design 组件库提供交互控件；Axios 进行 HTTP 调用；
5. 外部系统：
   对象存储用于文件管理；Redis 用于缓存与状态；数据库用于多租户数据隔离与审计。

## 2.6 现有工程框架的能力边界

LangChain 官方文档[4]提供了一套面向大语言模型应用开发的模块化工具链，涵盖提示模板管理、链式调用组装及外部数据源集成等核心组件的编程规范。当前开源生态为 LLM Agent 提供了丰富的编排工具，但在企业级部署中仍存在结构性缺陷。以 LangChain 为例，其链式抽象（Chain）与代理抽象（Agent）提供了快速组装能力，然而链的执行过程以黑盒方式收敛为最终文本输出，中间步骤的观测数据缺乏统一schema，难以直接用于离线评测或审计追溯。LangGraph 在 LangChain 基础上引入状态持久化与循环边，支持更复杂的控制流，但其图节点的输入输出类型由开发者自行约定，系统层面无法保证"计划—执行—校验"的完整性约束，导致不同开发者实现的同构图可能产生差异巨大的可解释性表现。
AutoGen 的核心贡献在于多智能体角色协作与对话驱动的任务分解，其群聊（GroupChat）机制适合需要多视角辩论或交叉验证的场景。但该框架对单智能体内部的工具调用链路缺乏细粒度管控，工具失败时的恢复策略依赖开发者手动编写回调，未形成可复用的失败处理范式。此外，上述框架的检索增强通常以向量存储（VectorStore）插件形式存在，召回策略固定为单路相似度检索，难以针对企业文档中常见的表格、术语定义等结构化片段进行优化。
本文工作不追求框架的通用性与图灵完备性，而是接受"单智能体、受限工具集、强审计需求"的约束，在垂直场景内做深做透：通过结构化的三阶段工作流替代开放的图节点，通过多策略召回替代单路向量检索，通过内建的租户隔离替代外部权限层，从而在企业知识问答与流程自动化场景中提供可预期、可评测、可运维的系统化方案。

# 3 方法框架与总体设计

## 3.1 闭环框架概述

本文提出的闭环框架以"规划-检索-推理-行动-记忆-反思"为核心，其设计前提并非替代通用的多智能体编排系统，而是针对单智能体在受控工具环境下的高可靠执行这一约束场景。与 LangGraph 等开放图编排框架不同，本框架<删除>将控制流固化为 Planner—Executor—Check 三阶段顺序结构，禁止任意跳过或乱序执行</删除><新增>将控制流组织为 Planner—Executor—Check 三阶段顺序结构，以减少执行过程中的随意性</新增>；与 AutoGen 等多智能体框架不同，本框架<删除>聚焦单智能体内部的工具调用链路，通过结构化的轨迹记录与强制校验提升可审计性</删除><新增>聚焦单智能体内部的工具调用链路，并通过结构化轨迹记录与结果校验增强过程可追踪性</新增>。<删除>这种"约束即特性"的设计哲学，牺牲了部分灵活性以换取工程可控性，适用于对过程可追溯、结果可验证有刚性需求的企业场景。</删除><新增>这种设计虽然降低了部分灵活性，但更适合本文原型系统所面向的文档问答与流程执行场景。</新增>

## 3.2 模块划分与接口

Fielding[3]在其博士论文中系统阐述了表征状态转移（REST）架构风格，强调通过统一接口、无状态通信及分层系统等约束条件，提升网络软件架构的可扩展性与松耦合性。基于此，为保证复用与可扩展性，我的原型系统以前后端分类和接口驱动的方式组织各模块：
状态与上下文：统一的 state/context 结构保存对话历史、工具调用结果、检索证据与运行元信息；
工具路由：对工具进行统一描述（名称、输入 schema、权限边界、超时与重试策略），并支持按任务类型选择工具；
轨迹记录：记录每一步的“思考—行动—观察—判定”，并支持回放与离线分析；
失败恢复：对常见失败（检索为空、工具报错、输出格式错误、权限不足）提供重试、降级与回滚策略。

## 3.3 Planner—Executor—Check 链式工作流

在原型系统中，智能体采用三阶段链式工作流：
Planner：根据用户目标生成步骤列表与工具调用计划，输出结构化计划；
Executor：按计划逐步调用工具或检索服务，并将观察结果写入轨迹；
Check：对阶段性输出进行一致性与目标达成检查，必要时触发修复（重新检索、改写参数、替换工具）或终止。
该设计将复杂任务执行拆解为可控单元，便于将不同策略进行对比与消融评测。

## 3.4 多租户与权限边界

企业应用场景下，多租户隔离与权限控制是系统可靠性的重要组成部分。原型系统在请求层引入租户标识与鉴权信息，并在数据访问与工具调用层强制执行租户边界，确保不同租户间数据隔离；同时对敏感工具（文件读取、外部 API、邮件等）限定可用范围与审计记录，降低越权风险。

## 3.5 轨迹记录与结构化数据模型

为了使智能体执行过程“可解释、可回放、可评测”，本文将关键中间产物结构化，并在链路执行时持续记录。结构化数据的核心目标有三点：其一，将 Planner 的计划转为可校验的数据结构，避免纯自然语言计划带来的歧义；其二，将 Executor 的工具调用过程记录为可枚举的日志，便于审计与复现；其三，将 Check 的评审输出结构化，便于统一收敛为“是否通过 + 得分 + 理由”，并将对工具的细粒度评价反馈到系统治理中。

### 3.5.1 计划结构

计划至少包含两类信息：一是执行链路（execution_chain），用于指定工具/服务调用的推荐顺序；二是工具装配配置（mcp_config），描述每个 MCP 服务的连接方式与启动参数。除此之外，Planner 还可以给出补充指示（instructions），用于约束 Executor 的策略偏好，例如“必须先检索再总结”“输出必须带引用”等。

### 3.5.2 执行轨迹

在 Executor 阶段，系统将每一次工具调用抽象为 ToolCall，包括工具名、状态、输入、输出以及所属服务器（server）。这种形式既能支持流式前端展示（逐条工具调用的开始与结束事件），也能支持离线评测（统计工具调用次数、失败率、平均耗时等）。

### 3.5.3 校验结果

在 Check 阶段，系统将“目标信息（Object）”与“事实信息（Fact）”组合后交给校验 Agent 进行判断。CheckOutput 包含 judge（是否通过）、score（1–100）、reasoning（理由），以及工具级评估列表 tool_assessments。工具级评估以 micro_score 与 micro_judge 描述单工具质量，可用于“工具可信度更新”“问题回放定位”等治理环节。

**表 3.1 关键结构化数据字段（摘要）**

| 模型           | 字段                    | 含义             | 典型用途                     |
| -------------- | ----------------------- | ---------------- | ---------------------------- |
| WorkflowPlan   | execution_chain         | 推荐调用顺序列表 | 约束 Executor 按顺序调用工具 |
| WorkflowPlan   | mcp_config              | MCP 连接配置列表 | 构建多服务器 MCP 客户端      |
| WorkflowPlan   | instructions            | 执行补充约束     | 降低“工具会用但用不好”的概率 |
| ToolCall       | name/status             | 工具名/调用状态  | 统计失败率与可靠性           |
| ToolCall       | input/output            | 输入/输出快照    | 审计、复盘、回放             |
| CheckOutput    | judge/score             | 通过与评分       | 决策是否终止或重试           |
| ToolAssessment | micro_score/micro_judge | 工具级评价       | 更新工具可信度与路由策略     |

## 3.6 失败恢复与反思机制设计

在开放环境中，失败往往来自“信息不足”“工具不可用”“格式不符合约束”“权限边界触发”等因素。为了提升系统可靠性，本文将失败恢复视为闭环中的一等公民，并采用“可检测—可定位—可恢复”的工程策略组织流程。

### 3.6.1 失败检测。

系统在 Planner/Executor/Check 三个阶段分别引入失败检测点：Planner 阶段检测是否返回结构化计划；Executor 阶段检测 MCP 客户端是否初始化成功、工具列表是否获取成功、工具调用是否异常；Check 阶段检测 judge/score 是否满足阈值（例如 score≥80 视为通过）。

### 3.6.2 失败定位。

系统将每一步骤状态写入 steps，并将工具调用序列写入 tool_calls。这样在失败发生时，可以基于“阶段 + 工具名 + 输入输出”进行定位，而不是仅依赖最终自然语言文本。

### 3.6.3 恢复策略。

恢复策略以“回退到规划阶段并重新规划”为主，辅以“重试”“降级”“缩小任务范围”等提示。具体地，当 Check 判定不通过时，系统清理 ctx.plan 并回到 Planner 生成新计划；当达到最大步数限制时，系统输出友好提示，引导用户调整输入或提升上限。

## 3.7 工具可信度与路由策略

工具调用稳定性是智能体工程落地的关键瓶颈之一。本文原型系统引入“工具可信度更新”机制：校验阶段输出 tool_assessments（逐工具 micro_score/micro_judge），并将评估结果映射到具体 MCP 配置项，更新其可信度分数或状态。该机制使得系统能够在长期运行中逐步积累“哪些工具在什么场景下可靠”的经验，为后续的工具路由、默认排序与降级策略提供依据。

## 3.8 设计目标与原则

本文框架与系统实现遵循以下设计原则：

1. 可解释性：
   任何最终输出均尽量具备可回溯的中间轨迹；
2. 可审计性：
   工具调用输入输出可被记录与回放，支持问题定位；
3. 可扩展性：
   工具与检索策略可插拔，支持多源数据与多工具生态；
4. 可评测性：
   以结构化日志支持统一指标计算与回归对比；
5. 安全边界：
   以多租户隔离、权限控制与敏感信息治理降低风险。

# 4 系统实现

## 4.1 总体架构

原型系统 Agentlz 采用前后端分离架构。后端以 FastAPI 提供统一 /v1 API，按“路由—服务—仓储”分层组织业务；前端基于 React-Admin 构建管理控制台，负责智能体配置、文档管理、测评与运行监控等交互。系统通过 WebSocket 实时推送执行进度与结果，通过消息队列异步消费长耗时任务（如测评、文件处理、索引构建），并结合数据库与缓存进行状态管理。
从一次典型交互流程看，用户在前端提交任务后，后端进入链式工作流并通过 SSE 将过程事件持续推送给前端；当涉及耗时任务（例如测评与文档处理）时，系统将任务投递到消息队列，由后台消费者异步处理，并使用 WebSocket 推送进度。本设计同时兼顾了“面向交互的流式体验”和“面向吞吐的异步处理”。

## 4.2 后端实现（FastAPI）

后端实现要点如下：

1. 路由层
   按领域拆分路由模块（如 auth、agent、chain、document、evaluation、mcp、uploads、ws 等），并在应用入口统一挂载；
2. 服务层
   封装核心业务逻辑与跨模块协作（如智能体编排、RAG 文档处理、测评调度、缓存与队列交互）；
3. 仓储层
   面向数据库表的 CRUD 与查询封装，统一承载多租户隔离条件与分页排序逻辑；
4. 异常与响应
   统一返回结构，区分参数校验错误与服务内部错误，保证接口合同稳定；
5. 外部服务
   封装数据库、对象存储、向量库、消息队列等连接管理，支持启动/关闭的生命周期治理。

### 4.2.1 统一响应体与异常处理

为保证前后端联调稳定性，系统采用统一响应结构 Result，成功与失败均以一致的字段组织数据；同时在应用入口处注册 HTTPException、参数校验异常与通用异常的处理器，避免未捕获异常导致前端难以识别错误类型。在工程实践中，统一响应体与统一异常处理能够显著降低接口变更对前端的影响，并提升问题定位效率。

### 4.2.2 SSE 流式链路接口设计

系统提供基于 SSE（Server-Sent Events）的流式接口，用于前端实时展示 Planner/Executor/Check 的过程事件。接口以 /v1/chat 形式对外暴露，前端可以按照事件类型增量渲染不同内容区。事件类型设计遵循“阶段事件 + 内容事件”的原则，典型包括：
chain.step：指示当前阶段（planner/executor/check）；
planner.plan：返回结构化计划（WorkflowPlan）；
call.start/call.end：单次工具调用开始/结束（ToolCall）；
check.summary：校验结果摘要（CheckOutput）；
final：最终输出。
这种事件分层设计有利于将“过程可视化”与“最终结果展示”解耦，提升交互透明度。

### 4.2.3 责任链执行与步数上限控制

链式工作流以责任链模式组织：从 Root 节点启动后，依次进入 Planner、Executor 与 Check。系统支持最大步数限制（max_steps），并设置硬上限（hard_limit）防止滥用造成资源占用。当达到最大步数时，系统以兜底文本提示用户缩小任务或调整上限，避免“无限循环规划—执行—校验”的风险。

### 4.2.4 WebSocket 会话管理与主题发布

系统实现了轻量级 WebSocket 连接管理器，用于维护“连接—用户—租户”的映射，并支持基于 topic 的订阅发布。该机制适用于推送长耗时任务的进度（例如测评运行、上传处理、批量解析），避免前端频繁轮询带来的资源浪费。工程上采用“按用户推送（send_to_user）+ 按主题推送（publish）”两种路径，可兼顾个体通知与广播场景。

## 4.3 智能体编排与工具系统

系统将提示词模板、数据结构与执行逻辑解耦：提示词按 agent 类型分类管理；请求/响应结构由 Pydantic schema 统一约束；工具以轻量适配器形式暴露能力，并通过路由策略选择使用。智能体执行过程产生可回溯轨迹，用于评测、审计与问题定位。

### 4.3.1 Planner 实现：结构化计划生成

Planner 阶段的目标是想将用户自然语言目标转为可执行计划。系统通过系统提示词约束 Planner 输出结构化计划（WorkflowPlan），并为 Planner 注册“按关键词检索 MCP 配置”的工具，使其能够根据用户意图选择合适的工具链。为了保证工程可用性，当模型不可用或未返回结构化计划时，Planner 会返回兜底计划并写明失败原因，避免链路直接崩溃。

### 4.3.2 Executor 实现：多 MCP 工具接入与日志采集

Executor 阶段根据 Planner 计划装配 MCP 工具集，并支持 stdio/http/sse 等多种传输方式。执行过程中，系统通过回调拦截器采集工具调用日志：在工具调用开始时推送 call.start 事件，在工具调用结束时推送 call.end 事件，并将输入输出结构化保存。该机制既提高了前端过程展示能力，也为离线评测提供了可计算的数据基础。

### 4.3.3 Check 实现：结构化评审与回退控制

Check 阶段将“目标信息（Object）”与“事实信息（Fact）”拼接，并附带工具调用日志 JSON，交由校验 Agent 输出 CheckOutput。系统统一用 judge 或 score（阈值 80）判定是否通过；未通过时清空旧计划并回退到 Planner 重新规划。该策略相比“单次执行直接返回”更适合复杂任务，可提升最终达成率并减少明显错误的输出。

## 4.4 检索增强链路实现

RAG 模块的技术选型遵循"召回优先、生成兜底"的原则，在文档生命周期各阶段采用如下实现方案：

1. 上传与解析
   后端接收文件后，依据 MIME 类型分发解析器。PDF 采用 PyMuPDF 提取文本与坐标信息，保留页码用于溯源；Office 文档通过 python-docx 与 openpyxl 解析，表格内容转换为 Markdown 管道符格式以维持结构；纯文本直接读取。解析产物经过去重与编码归一化（统一为 UTF-8）后进入切分阶段。
2. 切分与嵌入
   采用递归字符切分策略（RecursiveCharacterTextSplitter），分隔符优先级为段落符（\n\n）→ 换行符（\n）→ 句号（。/ .）→ 空字符，块大小（chunk_size）设为 512 字符，重叠（overlap）设为 64 字符，以保证语义连续性。嵌入模型选用 BAAI/bge-large-zh-v1.5（1024 维），通过 sentence-transformers` 加载，向量相似度采用余弦距离（cosine similarity）。
3. 索引与检索
   向量索引采用 pgvector 扩展（PostgreSQL 16），向量维度 1024，相似度检索使用 <=> 运算符（余弦距离）。除向量召回外，系统并行执行 BM25 词项匹配，采用 rank-bm25 库基于jieba分词构建稀疏索引，默认召回 Top-10。两路结果通过 RRF（Reciprocal Rank Fusion）融合，k 值取 60，最终取 Top-5 送入生成阶段。

### 4.4.1 多链路召回与融合重排

在实际检索中，仅依赖单一向量召回容易出现“语义近但事实不相关”或“关键词命中强但语义不够”的问题。为此，系统引入多链路召回：一方面使用向量相似度召回候选块；另一方面使用 BM25 等词项匹配召回候选块；必要时再进行融合重排（rerank），得到最终 Top-K 上下文片段。该策略在中文企业文档场景下更稳健，尤其适用于术语密集、格式化内容较多的材料。

### 4.4.2 查询改写与上下文组装

为提升召回质量，系统可以先对用户输入进行查询改写，得到多个子查询短句，再分别召回并融合。随后对召回结果进行去重、排序与裁剪，组装为最终可注入模型的上下文。工程上通过“限制词条数量”“限制最终 Top-K”控制上下文规模，避免长上下文导致的成本与遗忘问题。

### 4.4.3 召回性能基线与策略对比

为验证多链路召回的有效性，在内部测试集（50 条企业文档问答对）上对比不同召回策略的命中率。测试集覆盖事实检索（40%）、数值比对（30%）与多文档综合（30%）三类问题。

**表 4.1 召回策略对比（测试集 50 条）**

| 策略               | Top-5 命中率 | 平均召回数 | 首条相关平均位次 | 备注                       |
| ------------------ | ------------ | ---------- | ---------------- | -------------------------- |
| 纯向量召回         | 68%          | 5.0        | 2.3              | 语义相近但术语不匹配时失效 |
| 纯BM25召回         | 54%          | 5.0        | 3.1              | 关键词命中强但语义泛化弱   |
| 向量+BM25融合(RRF) | 82%          | 5.0        | 1.8              | 兼顾语义与词项匹配         |
| 融合+查询改写      | 88%          | 7.2        | 1.5              | 改写带来冗余，需去重裁剪   |

## 4.5 异步任务与实时推送

为提升系统吞吐与交互体验，系统引入消息队列承载异步任务，并在执行过程中通过 WebSocket 推送进度与结果。典型异步任务包括：测评任务分批执行、文件解析与索引构建、长链路工具调用等。该设计使前端能够实时呈现中间过程，降低“黑盒执行”的不确定性。

### 4.5.1 测评任务的分批执行与进度聚合

在测评场景中，单次任务往往包含多条样例，若同步执行会导致接口超时且用户体验差。系统采用“分批执行 + 结果聚合”的策略：后端创建测评运行记录（含总数与已完成数），并投递 MQ 消息；消费者按 batch_size 拉取样例切片执行，每完成一条即更新聚合结果并推送进度；若未完成则发布下一条 MQ 消息继续执行；完成后写入 finished_at 并推送 done 事件。该策略将长任务拆解为可控的短任务单元，能够有效提升鲁棒性与可恢复性。

## 4.6 前端实现（React）

前端基于 React-Admin 组织页面与数据源调用，实现以下能力
用户与租户管理、鉴权登录；智能体配置与运行入口；文档上传、检索与 RAG 管理；测评数据集管理、评测启动、结果回放与可视化；WebSocket 连接监控与运行状态展示。

### 4.6.1 前后端分离的接口联调方式

首先，React-Admin通过声明式数据提供者与权限控制，为后台管理系统提供了可复用的页面组织模式[7] ，前端以 Axios 为基础实现统一的 httpClient，并按领域封装 API 模块（如 evaluation、rag、agent、mcp 等）。这种组织方式能够让页面组件更聚焦于交互逻辑，而不是请求拼装细节；同时便于在接口变更时集中修改调用层，降低维护成本。

# 5 实验设计与评测

## 5.1 任务集设计

实验选择 3–5 类代表性任务场景，以覆盖“检索—工具—多步执行”的典型链路

1. 信息检索问答：
   基于上传文档进行事实性问答与引用溯源；
2. 复杂任务分解：
   对目标进行多步规划并执行，评估计划质量与执行稳定性；
3. 跨模块协作：
   结合检索、工具调用与结果校验，评估闭环有效性；
4. 工程任务：
   文件上传/解析、测评任务分批执行与实时推送等工程能力验证。

## 5.2 评测指标

指标体系从以下维度衡量：
准确性与任务成功率：最终输出是否满足目标；
效率：平均步数、平均耗时与 token/调用成本（可选）；
可解释性：轨迹是否完整、可回放且关键决策有据可依；
鲁棒性：在检索噪声、工具失败与网络波动下的恢复能力；
安全性：是否存在越权访问、敏感信息泄露与不当工具调用。

## 5.3 对比基线与消融设置

对比对象可包含：无检索/仅检索、无记忆/仅记忆、CoT、Plan-then-Act 等策略；消融实验围绕规划模块、检索策略、校验与反思机制分别移除或替换，以量化各模块贡献。

## 5.4 实验环境与实现细节

为保证实验可复现性，需要对实现细节进行记录，包括运行环境、模型与关键参数、以及评测脚本的输入输出约定。

1. 运行环境
   后端服务基于 Python 运行环境与 FastAPI 框架，采用 /v1 API 对外提供服务；前端采用 React + React-Admin 作为管理控制台；链式工作流通过 SSE 推送过程事件；异步任务通过消息队列消费并用 WebSocket 推送进度。
2. 模型与参数
   智能体侧包含 Planner/Executor/Check 三类提示词模板；检索侧包含嵌入模型（用于向量化）与可选的重排模型（用于 rerank）。在论文中应记录：嵌入模型名称、向量维度、相似度度量方式（cosine/euclidean）、Top-K 参数（如 rag_vector_top_k、rag_bm25_top_k、rag_final_top_k），以及是否启用重排（rag_rerank_enabled）。
3. 数据与格式
   测评数据集建议采用 alpaca 格式数组，每条样例包含 instruction/input/output（或 fact_output）等字段，以便统一驱动智能体生成并比对结果。对于非 alpaca 的原始数据（如纯文本/Markdown），可先通过占位转换接口转为 alpaca，再进入评测链路，保证流程闭环。

## 5.5 结果展示方式与统计口径

考虑到不同任务的“正确性定义”差异较大，本文采用“定量 + 定性”结合的方式展示结果，并明确统计口径，避免因口径不一致导致结论失真。

1. 定量展示
   对每个任务场景统计：任务成功率、平均步数、平均耗时、工具失败率、以及校验通过率。对于检索问答场景，还应统计引用命中率（回答中是否包含来源片段）与证据覆盖率（关键结论是否能在召回片段中找到对应依据）。
2. 定性展示
   给出 2–3 条代表性轨迹：包含 Planner 计划、Executor 工具调用序列、Check 评分与理由，以及最终输出。定性分析重点讨论：失败发生在哪个阶段、是否能通过回退重新规划修复、以及修复成本（额外步数与额外工具调用）。

| -------- | --------------------- | ------- | --------- | --------- | ----------- | ----------- |

## 5.6 典型失败类型与案例分析

结合原型系统的执行轨迹与日志，可以将失败样例归纳为以下几类，并给出对应改进方向。

1. 检索证据不足
   表现为：召回片段为空或与问题弱相关，导致生成阶段凭空补全。改进策略：启用多链路召回（向量 + BM25）、增加查询改写、提升文档切分质量、引入重排模型对候选片段二次排序。
2. 工具参数错误或工具不可用
   表现为：MCP 客户端初始化失败、工具列表获取失败、或工具输入输出格式不符合预期。改进策略：在 Planner 中加入“工具输入 schema 提示”，在 Executor 中加入工具调用前的参数校验与兜底（例如无工具可用时转为纯检索/纯总结），并记录失败原因用于后续治理。
3. 输出格式不合规
   表现为：模型未按结构化格式返回，导致无法解析计划/评审结果。改进策略：使用结构化 response_format 约束输出；当解析失败时采用“兜底结构”继续推进，避免链路中断，同时在 Check 中给出扣分与修复建议。
4. 权限边界触发
   表现为：跨租户访问文档、调用敏感工具或访问未授权资源被拒绝。改进策略：在工具描述中显式声明权限边界，Planner 生成计划时优先选择“低权限可用工具”，并将权限错误作为可恢复错误回退到 Planner 重选工具链。

**表 5.2 失败类型归因与处置策略**

| 失败类型   | 触发阶段  | 可观测信号                 | 处置策略                       |
| ---------- | --------- | -------------------------- | ------------------------------ |
| 召回为空   | 检索/执行 | Top-K 为空或相似度过低     | 查询改写 + 多路召回 + 降级总结 |
| 工具不可用 | 执行      | client_init/get_tools 异常 | 记录错误 + 回退重选工具        |
| 格式错误   | 规划/校验 | structured_response 为空   | 兜底结构 + 提示词强化          |
| 越权       | 任意      | 403/权限错误               | 权限提示 + 回退 + 审计         |

## 5.7 系统测试与可用性验证

为了验证原型系统在工程层面的可用性，除算法与策略对比外，还需要进行系统测试与联调验证。本研究采用“分层测试 + 场景回归”的方式组织测试工作。

1. 接口可用性测试
   对核心接口进行最小闭环验证：鉴权登录、租户头解析、SSE 流式接口返回、WebSocket 订阅与推送、测评数据集 CRUD、测评启动与历史查询、文档上传与检索等。测试重点关注：返回结构是否稳定、错误码是否准确、分页与筛选参数是否符合预期。
2. 链路回归测试
   对 Planner→Executor→Check 链路进行回归：相同输入在相同配置下应能得到一致的结构化计划与可解析的评审输出；当工具不可用或检索为空时，系统应返回可解释的错误与降级结果，而不是崩溃或无响应。
3. 数据一致性测试
   对测评任务的“分批执行 + 结果聚合”链路进行一致性检查：completed_count 应单调递增且不超过 total_count；content_json 的条目数量应与 completed_count 对齐；任务结束后状态应从 running 进入 done 或 failed，并写入完成时间。
4. 前后端联调验证
   通过前端页面对测评、文档与智能体运行进行联调，验证表格渲染、进度展示与错误提示的完整性。对比纯轮询模式，SSE/WS 推送模式能够显著降低交互等待感，并提升用户对执行过程的可理解性。

# 6 应用案例与分析

## 6.1 企业知识检索与问答

系统支持上传企业文档并构建向量索引，用户可通过智能体进行问答与信息抽取。通过检索增强与来源标注，可降低幻觉风险并提升可解释性。

## 6.2 测评系统与可回放轨迹

系统支持对智能体进行版本快照与测评运行记录管理，将测评任务异步执行并实时推送进度，便于对不同版本提示词/策略进行对比与回归验证。

## 6.3 大文件上传与安全治理

面向工程落地场景，系统支持小文件直传与大文件分片上传，并引入病毒扫描、完整性校验与隔离区（quarantine）策略，避免恶意文件进入解析链路，提升安全性与合规性。
在工程实践中，文件上传与解析属于高风险链路：一方面文件体积可能很大，若全部经由后端转发会形成带宽与存储瓶颈；另一方面文件内容可能包含恶意载荷，若不经过扫描与隔离就进入解析与索引，将带来安全隐患。因此，本文将上传链路划分为两条策略路径：小文件走“简单上传”，大文件走“分片上传 + 断点续传 + 前端直传对象存储”，并在上传完成后引入扫描 gating，只有 scan_status==passed 的文件才能进入解析与切块入库。
小文件上传链路。文件体积小于阈值时，可由后端接收文件并写入对象存储，随后触发扫描任务；扫描通过后再进入文档解析与向量化流程。该链路实现成本低，适合交互式上传。
大文件分片上传链路。文件体积大于阈值时，前端通过后端获取分片的预签名上传 URL，将分片直接上传至对象存储；后端仅负责签名与任务状态机管理，避免带宽瓶颈。上传完成后，后端提交 complete 操作并触发扫描；扫描通过后，将对象从 quarantine 前缀“转正”至可访问前缀，再触发解析与入库。

完整性校验与断点续传。系统可对文件计算 hash，并对每个分片记录 etag/part_hash，用于断点续传与一致性对账；当网络中断或刷新页面时，前端可根据已上传分片列表继续上传剩余分片，降低失败重传成本。
安全治理与审计。对上传、扫描、解析等状态进行显式建模，并记录关键操作日志，可为后续安全审计与责任追踪提供依据；同时通过租户隔离保证不同租户文件互不可见，降低跨租户泄露风险。

## 6.4 案例 1：流式链路的可视化执行

本案例展示用户通过流式接口触发链式工作流，并实时观察 Planner/Executor/Check 的过程输出。与传统“一问一答”不同，用户可以看到：系统是否进行了规划、是否调用了工具、以及校验是否通过，从而降低“黑盒交互”的不确定性。
用户输入示例：给出一个需要多步完成的任务目标，例如“根据某份文档回答某条事实，并给出依据”。
SSE 事件流示例：前端按事件类型消费并渲染。
从工程角度看，SSE 事件将“过程状态”与“内容负载”分离，使得前端能够对不同阶段采取不同展示策略：例如 planner.plan 渲染为结构化计划视图，call.start/end 渲染为工具调用列表与展开详情，check.summary 渲染为评分与理由面板，final 作为最终答案展示。

## 6.5 案例 2：测评任务的异步执行与结果回放

本案例展示系统对某个 Agent 进行测评：先选择测评集与目标 Agent，然后启动测评任务；后端投递消息队列并分批执行；前端通过 WebSocket 接收进度与单条结果，支持最终结果回放。
测评启动。用户选择测评集后调用启动接口，后端返回 eva_content_id 与 eva_version_id，标识本次测评运行与版本快照。
进度推送。后台消费者每处理一条样例，更新 completed_count，并推送 item_done；全部完成后推送 done。
结果回放。测评结束后，用户可以按 agent_id 查询版本列表与历史测评记录，并查看某次 eva_content 的 content_json 聚合结果，实现“可回放、可对比、可追踪”的评测闭环。

# 7 讨论与展望

## 7.1 局限性

1. 模型能力边界：
   在高不确定任务中仍可能产生幻觉或错误计划；
2. 检索质量依赖：
   索引质量与切分策略对结果影响显著；
3. 工具生态复杂：
   外部工具的可用性、权限与失败模式多样，工程治理成本较高；
4. 评测基准不足：
   通用评测集难以覆盖企业特定流程与数据分布。

## 7.2 安全与伦理

应从权限控制、敏感信息过滤、审计日志与失败回滚等方面构建治理机制，明确系统使用边界与责任约束，降低越权与误用风险。

# 8 结论

本文围绕 LLM 智能体在开放场景中的可靠性与工程落地难题，提出了以“规划—检索—推理—行动—记忆—反思”为核心的闭环框架，并实现前后端分离原型系统 Agentlz。系统通过 Planner—Executor—Check 链式工作流提升多步任务执行的可控性，通过 RAG 链路增强知识注入与证据可追溯性，通过 WebSocket 与消息队列实现异步执行与实时反馈，并结合多租户鉴权与审计机制提升可运维性与安全性。实验设计与原型验证表明：<删除>闭环框架在复杂任务场景下具有较好的可用性与可扩展性，为构建企业级 LLM Agent 提供了可实现的参考架构与工程范式。</删除><新增>该原型系统能够较完整地支持文档问答与多步任务执行流程，并在过程展示、结果回放和异常处理方面体现出一定可用性，可为后续同类系统的设计与实现提供参考。</新增>
